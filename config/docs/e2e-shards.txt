# e2e shard plan — how many shards each suite is split into.
#
# One file, two readers: the nightly's `plan` job reads it to build its matrix,
# and `scripts/e2e-shard-plan.py` reads it to tell somebody which flows a red
# shard holds and how to run that shard locally. The number used to live only
# in the workflow, so a local reproduction had to guess it — and a guess of 3
# against a nightly that used 4 runs different flows, because the shard is
# `index % shards`.
#
# Only the count belongs here. *Which* flows a suite runs is the runner's
# business — the smoke suite is selected by tag, the full suite is every flow
# — and the runner is the single source of that fact. A plan that repeated the
# selection would be a second place for it to be wrong.
#
# Rewrite with: edit this file. A change here changes the nightly's matrix,
# so it is a deliberate act, not a side effect of adding a flow.
#
# Format: <suite> <shard count>
#
# The smoke suite runs on 4 shards, not 1. It used to run on 1: one runner did
# the whole tag-selected suite while the nightly split every flow over four, so
# the "minimal regression suite" cost nearly a full-suite shard on a single
# runner and was the longest thing in the workflow. The shard is taken over the
# tag-selected flows and not over every flow, so the four shards hold the same
# 27 flows between them in shares of 7, 7, 7 and 6 — each about a third of a
# full-suite shard. Sharding over every flow and filtering afterwards gave
# shares of 7, 9, 4 and 7, and the runner waiting on the largest one set the
# wall clock for every pull request.
#
# Both suites therefore cost the same number of runners, and the pull-request
# path finishes in a third of the wall clock it used to take.

full 4
smoke 4
