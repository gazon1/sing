# A test that fails in one run and passes in the next has proven itself
# nondeterministic, whatever either run reported. Listing it here records that
# the nondeterminism is *understood* — a failure not on this list is a real
# failure, and the gate says so.
#
# An entry is either a full `class::case` id or a bare class name, which
# acknowledges every test in that class. Prefer the class form: flakiness
# usually comes from a shared fixture or a real-clock wait, not from one
# assertion.
#
# Removing a line is the goal, not a formality. If an entry has not failed in
# 30 days, delete it and fix whatever made it flaky.
#
# Format: <class or class::case>  # why it is nondeterministic, and what is known

com.singularity.todo.core.process.ProcessTreeTest  # The tree's grace period is measured on the test's virtual clock, and the operating system's reaping of a killed process is not: the process has to die in real time, and a host under load takes longer at it. Failed once on a full :shared:jvmTest at load 38 ("the graceful path still ends it") and passed on the next run in isolation. The wait belongs to ProcessTree.awaitExit, and it is virtual in a test and real in production; the fix is a real-clock wait there, not a re-run here.
com.singularity.todo.test.helpers.CoroutineDiagnosticsTest  # Every case in this class calls the kotlinx-coroutines-debug agent's dump, and that agent's overhead is a suspect this repository has already recorded (docs/decisions/2026-10-07-a-fork-that-died-left-no-evidence.md, hypothesis 2). Observed once on a full :desktopApp:test at load 41 with :shared:jvmTest running in the same command: each dump took about a minute, past runTest's 60-second budget, so three of the four cases were reported as "the test body did not run to completion" and the class took 266 s. The same class in isolation took 1.6 s and passed. The wait is the agent's, not the test's; the fix is a host that is not saturated, not a re-run here.
