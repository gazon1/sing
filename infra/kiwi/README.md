# Kiwi TCMS — локальный стенд тест-кейсов

## Что это решает

В проекте уже есть два ответа на вопрос «что с тестами»:

| Вопрос | Кто отвечает | Чего не говорит |
|---|---|---|
| «сколько строк кода покрыто» | `scripts/check-coverage.py` (Kover) | какие **намерения** проверяются |
| «сколько тестов написано» | `find … -name '*Test.kt'` | какие из них **запускались** |

Kiwi TCMS добавляет недостающий слой: **тест-кейс — это утверждение о поведении,
у него есть статус последнего прогона**. Кейс, который ни разу не запускался,
оказывается видимым как «не проверено», и это ровно тот список дыр, который
иначе не существует ни в одном отчёте.

Киви **не запускает тесты**. Это база знаний о тестах: она хранит кейсы,
прогоны и результаты, а запускает Gradle. Связь с репозиторием делает
`sync.py` — он читает исходники и JUnit XML.

## Быстрый старт

```bash
./infra/kiwi/up.sh                 # поднять стенд (разово ~2-3 мин на холодном старте)
./infra/kiwi/sync.py --plan         # залить 263 тест-класса как кейсы
./infra/kiwi/sync.py --results      # залить результаты последнего Gradle-прогона
./infra/kiwi/gaps.py                # что осталось непроверенным
```

Стенд: **https://127.0.0.1:8443** — логин `kiwi` / `kiwi`.

```bash
./infra/kiwi/down.sh                # остановить, данные сохранить
./infra/kiwi/down.sh --purge        # снести вместе с БД
```

## Фоновый режим (just)

Для повседневной работы есть рецепты: контейнеры живут между вызовами `just`.

```bash
just kiwi-start      # поднять в фоне, вернуться сразу (~6 с, БД НЕ инициализирована)
just kiwi-wait       # дождаться готовности и инициализировать БД (блокирует)
just kiwi-status     # контейнеры / HTTP / состояние БД
just kiwi-logs       # хвост логов Kiwi (-f)
just kiwi-stop       # остановить, данные сохранить
just kiwi-restart    # перезапустить и дождаться готовности
just kiwi-purge      # снести вместе с БД (спросит подтверждение)
```

Алиасы покороче: `just kiwi-up` (start + wait одним шагом), `just ksync`,
`just kresults`, `just kgaps`, `just kprune`, `just kfloor`.

## Гейт на «дыры» и ротация

`kover` меряет достигнутый код, `check-test-runs.py` — что вообще выполнилось.
Ни то, ни другое не видит класс, который **написан, помечен и ни разу не
запущен**. Это читает `scripts/check-kiwi-gaps.py` — единственный гейт проекта,
который видит Kiwi:

```bash
just kfloor                              # сверить с порогом
./scripts/check-kiwi-gaps.py --if-present   # пропустить, если стенд не поднят
./scripts/check-kiwi-gaps.py --max-age 24 # + требовать свежие данные
./scripts/check-kiwi-gaps.py --update-baseline
```

Порог хранится в `config/docs/kiwi-gaps-baseline.txt` — по плану, а не одним
числом: перенос теста между планами меняет два числа в разные стороны, и это
видно, тогда как одна сумма осталась бы прежней. План без строки пропускается:
у него нет честного прогона, из которого можно записать порог.

**Важное ограничение, о котором стоит помнить.** Гейт честен ровно настолько,
насколько свежи Kiwi. Стенд наполняет тот, кто запускает `kresults`, а в CI он
не запускается (см. ниже), поэтому зелёный `kfloor` — это утверждение о локальном
состоянии, а не о `main`. Это не гейт для мержей, и называть его гейтом нельзя.

Ротация:

```bash
just kprune                 # показать, что будет удалено (ничего не удаляет)
just kprune 40              # окно шире
just kprune apply           # удалить
./infra/kiwi/prune.py --apply --keep 20
```

Удаляются прогоны за пределами окна **по плану**; `TestRun.remove` каскадит на
execution'и, теги и свойства прогона, кейсы остаются. Окно по плану, а не по дате:
у `shared` прогоны каждый цикл, у `android instrumented` — почти никогда, и
возрастной фильтр стёр бы его историю целиком после первого неудачного месяца.

**Ротация и порог связаны.** «Никогда не запускался» читается из свойства
`ever_run` на самом кейсе, а не из живых execution'ов: `TestRun.remove` удаляет
и execution'и, поэтому метрика по ним откатывалась бы на нетронутом коде. Это
проверялось на стенде — после `prune --keep 1` счётчик «дыр» подскочил с 47 до
237, не изменившись ни одним тестом.

## Почему в CI это не работает

Стенд живёт на `127.0.0.1` этой машины, а джобы CI идут на эфемерных
GitHub-hosted раннерах в другой сети. Ни self-hosted раннера, ни публичного
адреса у стенда нет, поэтому шаг `kresults` в CI нельзя просто добавить в
`ci.yml` — он упал бы на подключении. Варианты разобраны в ADR
`2026-10-05-kiwi-gates-and-rotation`; выбор за владельцем репозитория.

**`kiwi-start` и `kiwi-wait` разделены намеренно.** `kiwi-start` только
запускает контейнеры: на холодном старте инициализация кластера Postgres
занимает ~2 минуты, и «поднять в фоне» не может означать «и БД готова».
До завершения миграций Kiwi отдаёт 500 на `/` — это ожидаемо, а не поломка;
`just kiwi-status` показывает это явно отдельной строкой, а `kiwi-wait`
догоняет инициализацию.

## Модель

```
Product  «Singularity Todo»
  Plan   «Automated — shared (commonTest+jvmTest)»
    TestCase                        ← один тестовый класс репозитория
      TestRun                       ← один запуск ./gradlew … test
        TestExecution               ← результат этого класса
```

> ⚠️ **Инвариант ниже устарел.** Он заменён на «кейс = пользовательский сценарий»
> (ADR `2026-10-05-scenario-test-cases-in-kiwi.md`). Старые планы `Automated/*`
> заморожены и продолжают работать как были — но новые сценарии заводятся
> **только** через `traceability/`, см. раздел «Сценарии и трассируемость».

**Кейс = тестовый класс, а не тестовый метод** (устаревший инвариант, см. выше).
Kiwi-идентификатор кейса обязан быть стабильным, а имя класса в Kotlin меняется
заметно реже, чем набор `@Test`-методов внутри.

Планы по модулям, а не по source set: `commonTest` и `jvmTest` компилируются в
**один** тестовый набор (`commonTest` исполняется задачей `jvmTest` — см.
`AGENTS.md`, раздел «Тесты»), и разносить их по разным планам значило бы
удвоить число кейсов без единого нового теста.

## Типичный цикл

```bash
# 1. прогнали тесты
./gradlew :shared:jvmTest -Ptest.tags=fast,slow

# 2. залили результаты
./infra/kiwi/sync.py --results

# 3. посмотрели, что не покрыто
./infra/kiwi/gaps.py
```

`sync.py --plan` достаточно запускать после появления новых тестовых классов
(он идемпотентен: повторный запуск не создаёт дубликатов, а обновляет
summary/приоритет/компонент у существующих).

## gaps.py — отчёт о пробелах

Три среза:

1. **Кейсы без прогона** — написаны, но ни разу не запускались. Главный сигнал.
2. **Компоненты без кейсов** — Kiwi-компоненты (feature.tasks, core.sync, …),
   где ноль кейсов: на фичу тестов нет вообще.
3. **Production-классы без теста по имени** — эвристика `NotesRepository` →
   `NotesRepositoryTest` в другом пакете. Это **кандидаты на проверку**, а не
   приговор: тест может называться иначе. Ложные срабатывания намеренно
   склоняются в сторону «меньше шума».

Флаги: `--markdown` (для issue/PR), `--json`, `--limit N`.

## Особенности стенда, о которых стоит знать

Эти пункты неочевидны и стоили отладки; каждое зафиксировано в коде на месте.

**HTTPS обязателен.** Порт 8080 внутри образа — это nginx-блок с
`return 301 https://$host$request_uri;`, он не отдаёт приложение. Backend
слушает 8443, и наружу публикуется он. Публиковать 8080 — значит получить
стенд, который на любой странице отвечает редиректом.

**Сертификат в образе непригоден.** Встроенный `localhost.crt` выдан хосту
сборки образа (`CN=buildkitsandbox`, в SAN нет ни `localhost`, ни IP), поэтому
`gen-tls.sh` генерирует свой, с `SAN=DNS:localhost,IP:127.0.0.1`. Ключ
выставляется 0644 — не по небрежности: контейнер стартует от uid 1001, и nginx
не может прочитать ключ 0600 root и падает на старте.

**Аутентификация идёт по session-cookie.** `Auth.login` возвращает ключ в
`Set-Cookie: sessionid`; `xmlrpc.client.Transport` cookie не запоминает, и
каждый следующий вызов приходит анонимным («Authentication failed» при верном
пароле). Отсюда `SessionTransport` в `kiwi_client.py`.

**Холодный старт Postgres занимает ~2 минуты.** На пустом volume
`kiwitcms/postgres` выполняется initdb. Поэтому в compose увеличены
`start_period`/`retries`: с дефолтными значениями `docker compose up` падает с
«dependency failed to start: … is unhealthy» при полностью рабочем Postgres.

**Образ `kiwitcms/postgres` падает на пустом volume.** Его единственный
init-скрипт `00_enable_ssl.sh` начинается с `set -eu` и сразу умирает на
`[ -z "$POSTGRES_SSL_CERT" ]` (unbound variable). Скрипт выполняется только при
первой инициализации кластера, то есть ровно на пустом volume: контейнер
завершается с кодом 1, и `docker compose up` падает с
«dependency failed to start» — причём причина в сообщении не упоминается.
Воспроизводится на минимальном compose из трёх строк, то есть дело не в Kiwi.
Поэтому в compose смонтирован пустой `postgres-initdb.d` поверх
`/docker-entrypoint-initdb.d` — штатный способ отключить init-скрипты
postgres-образа. SSL самому Postgres не нужен: трафик Kiwi→Postgres идёт по
внутренней сети Docker, наружу открыт только Kiwi.

**Kiwi 16 требует заполненных справочников.** `Product.create` требует
`classification`, `TestPlan.create` — `type` и `product_version`,
`TestCase.create` — `case_status`, `category` и `priority` (причём priority —
это `P1..P5`, а не `Priority.NORMAL`). Все они пусты на свежей БД; клиент
создаёт их по именам через `ensure_*`.

**Кейс не привязывается к плану через `TestCase.create`.** Ключ `plan` во
входных значениях принимается, но форма его игнорирует — связь живёт в
`TestCasePlan`. Нужен отдельный вызов `TestPlan.add_case`, иначе кейс
создаётся с `plan=None` и невидим ни в одном плане.

**`TestExecution.create` — голый ModelForm.** FK передаются pk, а не именами;
поле называется `case`, а не `testcase`; `build` обязателен и из прогона не
наследуется; `case_text_version` — NOT NULL IntegerField, который Kiwi
16 требует явно, хотя у `TestCase` самого такого поля уже нет.

**Свойства кейса фильтруются по `case`, а не `pk`.** У модели `Property` pk —
это id строки свойства, а не кейса. Запрос с `pk__in` не ошибался, а возвращал
свойство постороннего кейса — и sync видел «у кейса нет `source_path`»,
пересоздавая кейсы вместо обновления.

**`TestRun.add_case` в Kiwi 16 ломает прогон после первого кейса.** Метод
создаёт `TestExecution` с `sortkey=None`, а следующий вызов на том же прогоне
падает с `unsupported operand type(s) for +=: 'int' and 'NoneType'`
(`sortkey = 10; sortkey += last_te.sortkey`). Поэтому sync создаёт execution
напрямую, с явным `sortkey` — `add_case` в коде оставлен, но не вызывается
и кидает внятную ошибку.

**Идентификатор класса в JUnit XML — не `testsuite@name`.** Gradle пишет туда
имя с суффиксом платформы (`AgendaDslTest[jvm]`), которое не совпадает ни с
одним FQN репозитория. Класс берётся из `<testcase classname="…">`.

**Кейс = класс, но FQN не уникален.** `com.singularity.todo.test.helpers.CoroutineDiagnosticsTest`
есть и в `shared/src/jvmTest`, и в `desktopApp/src/jvmTest`. Ключом
идемпотентности служит `source_path` (путь к файлу), а не FQN; классы с
неоднозначным FQN исключаются из привязки результатов с явным предупреждением,
а не назначаются первому попавшемуся модулю.

**Build принадлежит версии плана, а не продукту.** `NewRunForm.populate()`
ограничивает список допустимых build'ов через
`Build.objects.filter(version_id=plan.product_version_id, is_active=True)`,
поэтому build другой версии даёт «Select a valid choice.»

## Автоматизация

Хотите, чтобы результаты CI-прогона попадали в Kiwi — добавьте шаг после тестов:

```yaml
- name: sync to Kiwi TCMS
  if: github.ref == 'refs/heads/main'
  run: |
    python3 infra/kiwi/sync.py --plan --results \
      --url "$KIWI_URL" --user "$KIWI_USER" --password "$KIWI_PASSWORD"
```

`--plan` в CI не нужен, если кейсы уже заведены: синк идемпотентен и без него,
но тогда новые тестовые классы не появятся. Учётные данные — в секретах CI,
не в репозитории.

## Прямые запросы к API

```python
import sys; sys.path.insert(0, 'infra/kiwi')
from kiwi_client import KiwiClient

c = KiwiClient().check_alive()
for product in c.get_products():
    print(product['id'], product['name'])
```

Стенд намеренно локальный: открытая регистрация, пароль по умолчанию `kiwi`,
`SECURE_SSL_REDIRECT` выключен. Для любого внешнего окружения всё это нужно
закрыть — см. `local_settings.py` и `docker-compose.yml`.

## Сценарии и трассируемость (`traceability/`)

Слой **поверх** стенда, отвечающий на вопрос, на который слой «кейс = класс»
ответить не может: *какие пользовательские сценарии мы проверяем, на какой
платформе, каким уровнем и с каким результатом*.

Одно предложение: **сценарий задан в Git, результат приходит из CI, Kiwi —
проекция.** Матрицы производные; руками не ведётся ничего.

### Слои и Ownership

| Слой | Что хранит | Направление |
|---|---|---|
| Git | спеки сценариев + связь с автоматизацией (`@DisplayName`, тег `scenario:`) | **истина** |
| CI | что фактически запускалось и с каким PASS/FAIL | **авторитетно** |
| Kiwi | кейсы и история прогонов | проекция, **никогда не гейт** |
| матрицы | производные представления | — |

Направление одно: **Git → Kiwi**. Обратного пути нет. Поле, отредактированное в
UI Kiwi, будет перезаписано следующим `seed` — поэтому у каждого кейса есть
`extra_link` на канонический спек и существует `seed --check`.

### Два артефакта, и они не взаимозаменяемы

| Артефакт | Где живёт | Свойство |
|---|---|---|
| Матрица **покрытия** | `docs/testing/coverage-matrix.md` — **в git** | детерминирована, CI перегенерирует и падает при расхождении |
| Матрица **результатов** | `build/traceability/result-matrix.md` — **артефакт CI** | один конкретный коммит, в git не попадает никогда |

Файл, смешивающий «кто это заявил» и «что прошло на abc1234», устаревает к моменту
мерджа и конфликтует между ветками. Поэтому он разделён.

Покрытие — трёхзначное, потому что «заявлено» и «покрыто» — разные факты:
`—` не заявлено · `○` заявлено, но автоматизации нет (**дыра**) · `●` покрыто.

### Спека сценария

`infra/kiwi/scenarios/<область>/<подобласть>/<ID>.yaml`. Таксономия задана
**один раз** — каталогом; префикс id (`TASK-REC`) проверяется против него, а
поле `area` выводится из пути, а не объявляется свободно. Спека **не ссылается**
на тесты и на Kiwi: связь живёт в коде, иначе появился бы второй источник истины.

```bash
just trace-validate        # спеки + связи + namespace; без стенда и сети, ~мс
just trace-coverage        # перегенерировать матрицу покрытия
just kiwi::trace-coverage-check   # упасть, если закоммиченная копия устарела
just trace-results         # нормализовать JUnit/Maestro XML → results.json
just trace-results maestro # то же, включая потоки Maestro
```

#### Полный прогон и подмножество: почему `--partial`

`traceability results` без флагов считает прогон **полным** и применяет два
правила, оба — про отсутствие результата: «заявленная цель не дала ни одного
тесткейса» и (REQ-13) «сценарий заявлен и запускался, но не дал результата».
Это верно для CI: там `-Ptest.tags=fast,slow`.

Локальный цикл из `AGENTS.md` — `./gradlew :desktopApp:test` без
`-Ptest.tags` — исключает `@Tag("slow")`, а **носитель каждого сценария помечен
`slow`**. На таком прогоне цель отрабатывает, пишет десятки посторонних XML и ни
одного тесткейса со сценарием, то есть ровно та форма, которую ловят оба
правила. Поэтому `just trace-results` передаёт `--partial`: подмножество
объявляется явно, и отсутствие в нём ничего не доказывает.

Отличить «отфильтровано тегом» от «сломан носитель» по XML нельзя: нормализатор
видит, что носитель есть в исходниках и что результата нет, но не знает, какой
набор тегов применялся. Это знание есть только у вызывающего.

Флаг подавляет **оба** правила, а не только пер-сценарное. Первая версия флага
молчала только про пер-сценарное — из предположения, что пер-таргетное к
фильтрации нечувствительно. Предположение опроверглось на реальном прогоне, и
`PartialRunScope` в `scripts/tests/test_traceability.py` теперь закрепляет
обратное: на частичном прогоне отсутствие не значит ничего.
`test_ci_does_not_pass_partial` и `test_local_recipe_does_pass_partial` защищают
обе обвязки — забытый в CI флаг отключил бы правило молча, а пропавший из
рецепта сломал бы локальный цикл.

### Связь: два носителя, одно пространство имён

| Носитель | Механизм | Что применяется |
|---|---|---|
| Kotlin | `@DisplayName("TASK-REC-01 …")` | user-flow тесты |
| Maestro | `tags: [scenario:TASK-REC-01, smoke]` | заголовок потока |

Id обязан быть **первым токеном**. Всё остальное — ошибка, а не повод для
«обработки»: две `@DisplayName` на методе, id не в начале, id без спека,
сценарий, заявленный двумя тестами.

### Правила, которые являются ошибками

Это не строгость ради строгости — каждое правило закрывает свой класс тихой
поломки:

| Правило | Что закрывает |
|---|---|
| заявленная цель дала **ноль** тесткейсов → ошибка | задача Gradle отработала вхолостую и отчиталась зелёной |
| id без спека → ошибка | заявление, на которое никто не может посмотреть |
| два теста на один сценарий → ошибка, **не** слияние | слияние скрывает ровно то расхождение, ради которого матрица и нужна |
| тесткейс без связи → **отбрасывается** | 259 legacy-тестов не превращаются в кейсы |
| результат чужого коммита → ошибка | «свежий» отчёт, описывающий старый код |
| смешанный файл результатов → ошибка | прогон, имя которого врёт о половине своих executions |
| сценарий **без** автоматизации → **не** ошибка | это дыра `○`, и дыра — это смысл |

### Kiwi: один прогон на (коммит, цель)

Именно это правило позволяет Android-✅ и Desktop-❌ сосуществовать на одном кейсе.
Два execution в одном прогоне — это одно и то же наблюдение, записанное дважды, и
читатель «последний execution победил» теряет статус по платформам.

```bash
just kiwi-seed-dry-run     # что изменится, ничего не записывая
just kiwi-seed             # спроецировать спеки (идемпотентно по id)
just kiwi-seed-check       # падать при расхождении Kiwi и спеков
just kiwi-publish          # results.json → Kiwi как история прогонов
```

`skipped` здесь отображается в `WAIVED` (так делает официальный
`kiwitcms-junit.xml-plugin`), тогда как `sync.py` historically отображает его в
`IDLE`. Это **зафиксированное расхождение**, а не недосмотр: вся таблица живёт в
одном месте — `kiwi_publish.OUTCOME_TO_KIWI`.

### Границы (честно)

- **CI не достучится до стенда**: `https://127.0.0.1:8443` доступен только с
  loopback. Пока это не решено, честная формулировка такая: *история Kiwi не
  свежее последнего локального прогона публикации.* Стенд намеренно не
  публиковался наружу и не туннелировался.
- **Kiwi не может сделать сборку красной.** Недоступность стенда — код выхода 3,
  намеренно отличный от 1, чтобы падение стенда не читалось как ошибка спеки.
- **Удаление в Kiwi — решение человека.** `seed` показывает дубликаты, а не
  удаляет их.
- **Ничего не удаляем молча**: восстановление — `just kiwi-purge`, после чего
  `seed` пересобирает весь слой сценариев из Git.

### Сценарии не мигрируют 259 существующих кейсов

Планы `Automated/*` заморожены как есть. Сценарии — отдельный слой для
пользовательского поведения; покрытие по классам остаётся на Kover. Смешивать их
в одной таблице значило бы получить две разные единицы в одной сетке.
