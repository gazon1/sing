# Kiwi TCMS — локальный стенд тест-кейсов

## Что это решает

В проекте уже есть два ответа на вопрос «что с тестами»:

| Вопрос | Кто отвечает | Чего не говорит |
|---|---|---|
| «сколько строк кода покрыто» | `scripts/check-coverage.py` (Kover) | какие **намерения** проверяются |
| «сколько тестов написано» | `find … -name '*Test.kt'` | какие из них **запускались** |

Kiwi TCMS добавляет недостающий слой: **тест-кейс — это утверждение о поведении,
у него есть статус последнего прогона**. Кейс, который ни разу не запускался,
оказывается видимым как «не проверено», и это ровно тот список дыр, который
иначе не существует ни в одном отчёте.

Киви **не запускает тесты**. Это база знаний о тестах: она хранит кейсы,
прогоны и результаты, а запускает Gradle. Связь с репозиторием делает
`sync.py` — он читает исходники и JUnit XML.

## Быстрый старт

```bash
./infra/kiwi/up.sh                 # поднять стенд (разово ~2-3 мин на холодном старте)
./infra/kiwi/sync.py --plan         # залить 263 тест-класса как кейсы
./infra/kiwi/sync.py --results      # залить результаты последнего Gradle-прогона
./infra/kiwi/gaps.py                # что осталось непроверенным
```

Стенд: **https://127.0.0.1:8443** — логин `kiwi` / `kiwi`.

```bash
./infra/kiwi/down.sh                # остановить, данные сохранить
./infra/kiwi/down.sh --purge        # снести вместе с БД
```

## Фоновый режим (just)

Для повседневной работы есть рецепты: контейнеры живут между вызовами `just`.

```bash
just kiwi-start      # поднять в фоне, вернуться сразу (~6 с, БД НЕ инициализирована)
just kiwi-wait       # дождаться готовности и инициализировать БД (блокирует)
just kiwi-status     # контейнеры / HTTP / состояние БД
just kiwi-logs       # хвост логов Kiwi (-f)
just kiwi-stop       # остановить, данные сохранить
just kiwi-restart    # перезапустить и дождаться готовности
just kiwi-purge      # снести вместе с БД (спросит подтверждение)
```

Алиасы покороче: `just kiwi-up` (start + wait одним шагом), `just ksync`,
`just kresults`, `just kgaps`.

**`kiwi-start` и `kiwi-wait` разделены намеренно.** `kiwi-start` только
запускает контейнеры: на холодном старте инициализация кластера Postgres
занимает ~2 минуты, и «поднять в фоне» не может означать «и БД готова».
До завершения миграций Kiwi отдаёт 500 на `/` — это ожидаемо, а не поломка;
`just kiwi-status` показывает это явно отдельной строкой, а `kiwi-wait`
догоняет инициализацию.

## Модель

```
Product  «Singularity Todo»
  Plan   «Automated — shared (commonTest+jvmTest)»
    TestCase                        ← один тестовый класс репозитория
      TestRun                       ← один запуск ./gradlew … test
        TestExecution               ← результат этого класса
```

**Кейс = тестовый класс, а не тестовый метод.** Kiwi-идентификатор кейса обязан
быть стабильным, а имя класса в Kotlin меняется заметно реже, чем набор
`@Test`-методов внутри. Смена сигнатуры теста не должна плодить кейс и рвать
историю прогонов.

Планы по модулям, а не по source set: `commonTest` и `jvmTest` компилируются в
**один** тестовый набор (`commonTest` исполняется задачей `jvmTest` — см.
`AGENTS.md`, раздел «Тесты»), и разносить их по разным планам значило бы
удвоить число кейсов без единого нового теста.

## Типичный цикл

```bash
# 1. прогнали тесты
./gradlew :shared:jvmTest -Ptest.tags=fast,slow

# 2. залили результаты
./infra/kiwi/sync.py --results

# 3. посмотрели, что не покрыто
./infra/kiwi/gaps.py
```

`sync.py --plan` достаточно запускать после появления новых тестовых классов
(он идемпотентен: повторный запуск не создаёт дубликатов, а обновляет
summary/приоритет/компонент у существующих).

## gaps.py — отчёт о пробелах

Три среза:

1. **Кейсы без прогона** — написаны, но ни разу не запускались. Главный сигнал.
2. **Компоненты без кейсов** — Kiwi-компоненты (feature.tasks, core.sync, …),
   где ноль кейсов: на фичу тестов нет вообще.
3. **Production-классы без теста по имени** — эвристика `NotesRepository` →
   `NotesRepositoryTest` в другом пакете. Это **кандидаты на проверку**, а не
   приговор: тест может называться иначе. Ложные срабатывания намеренно
   склоняются в сторону «меньше шума».

Флаги: `--markdown` (для issue/PR), `--json`, `--limit N`.

## Файлы

| Файл | Роль |
|---|---|
| `docker-compose.yml` | Kiwi + PostgreSQL 17 |
| `up.sh` / `down.sh` | запуск / остановка, идемпотентная инициализация |
| `status.sh` | состояние стенда: контейнеры, HTTP, инициализация БД |

| `sync.py` | скан репозитория → кейсы; JUnit XML → прогоны |
| `gaps.py` | отчёт о непокрытом |

## Особенности стенда, о которых стоит знать

Эти пункты неочевидны и стоили отладки; каждое зафиксировано в коде на месте.

**HTTPS обязателен.** Порт 8080 внутри образа — это nginx-блок с
`return 301 https://$host$request_uri;`, он не отдаёт приложение. Backend
слушает 8443, и наружу публикуется он. Публиковать 8080 — значит получить
стенд, который на любой странице отвечает редиректом.

**Сертификат в образе непригоден.** Встроенный `localhost.crt` выдан хосту
сборки образа (`CN=buildkitsandbox`, в SAN нет ни `localhost`, ни IP), поэтому
`gen-tls.sh` генерирует свой, с `SAN=DNS:localhost,IP:127.0.0.1`. Ключ
выставляется 0644 — не по небрежности: контейнер стартует от uid 1001, и nginx
не может прочитать ключ 0600 root и падает на старте.

**Аутентификация идёт по session-cookie.** `Auth.login` возвращает ключ в
`Set-Cookie: sessionid`; `xmlrpc.client.Transport` cookie не запоминает, и
каждый следующий вызов приходит анонимным («Authentication failed» при верном
пароле). Отсюда `SessionTransport` в `kiwi_client.py`.

**Холодный старт Postgres занимает ~2 минуты.** На пустом volume
`kiwitcms/postgres` выполняется initdb. Поэтому в compose увеличены
`start_period`/`retries`: с дефолтными значениями `docker compose up` падает с
«dependency failed to start: … is unhealthy» при полностью рабочем Postgres.

**Образ `kiwitcms/postgres` падает на пустом volume.** Его единственный
init-скрипт `00_enable_ssl.sh` начинается с `set -eu` и сразу умирает на
`[ -z "$POSTGRES_SSL_CERT" ]` (unbound variable). Скрипт выполняется только при
первой инициализации кластера, то есть ровно на пустом volume: контейнер
завершается с кодом 1, и `docker compose up` падает с
«dependency failed to start» — причём причина в сообщении не упоминается.
Воспроизводится на минимальном compose из трёх строк, то есть дело не в Kiwi.
Поэтому в compose смонтирован пустой `postgres-initdb.d` поверх
`/docker-entrypoint-initdb.d` — штатный способ отключить init-скрипты
postgres-образа. SSL самому Postgres не нужен: трафик Kiwi→Postgres идёт по
внутренней сети Docker, наружу открыт только Kiwi.

**Kiwi 16 требует заполненных справочников.** `Product.create` требует
`classification`, `TestPlan.create` — `type` и `product_version`,
`TestCase.create` — `case_status`, `category` и `priority` (причём priority —
это `P1..P5`, а не `Priority.NORMAL`). Все они пусты на свежей БД; клиент
создаёт их по именам через `ensure_*`.

**Кейс не привязывается к плану через `TestCase.create`.** Ключ `plan` во
входных значениях принимается, но форма его игнорирует — связь живёт в
`TestCasePlan`. Нужен отдельный вызов `TestPlan.add_case`, иначе кейс
создаётся с `plan=None` и невидим ни в одном плане.

**`TestExecution.create` — голый ModelForm.** FK передаются pk, а не именами;
поле называется `case`, а не `testcase`; `build` обязателен и из прогона не
наследуется; `case_text_version` — NOT NULL IntegerField, который Kiwi
16 требует явно, хотя у `TestCase` самого такого поля уже нет.

**Свойства кейса фильтруются по `case`, а не `pk`.** У модели `Property` pk —
это id строки свойства, а не кейса. Запрос с `pk__in` не ошибался, а возвращал
свойство постороннего кейса — и sync видел «у кейса нет `source_path`»,
пересоздавая кейсы вместо обновления.

**`TestRun.add_case` в Kiwi 16 ломает прогон после первого кейса.** Метод
создаёт `TestExecution` с `sortkey=None`, а следующий вызов на том же прогоне
падает с `unsupported operand type(s) for +=: 'int' and 'NoneType'`
(`sortkey = 10; sortkey += last_te.sortkey`). Поэтому sync создаёт execution
напрямую, с явным `sortkey` — `add_case` в коде оставлен, но не вызывается
и кидает внятную ошибку.

**Идентификатор класса в JUnit XML — не `testsuite@name`.** Gradle пишет туда
имя с суффиксом платформы (`AgendaDslTest[jvm]`), которое не совпадает ни с
одним FQN репозитория. Класс берётся из `<testcase classname="…">`.

**Кейс = класс, но FQN не уникален.** `com.singularity.todo.test.helpers.CoroutineDiagnosticsTest`
есть и в `shared/src/jvmTest`, и в `desktopApp/src/jvmTest`. Ключом
идемпотентности служит `source_path` (путь к файлу), а не FQN; классы с
неоднозначным FQN исключаются из привязки результатов с явным предупреждением,
а не назначаются первому попавшемуся модулю.

**Build принадлежит версии плана, а не продукту.** `NewRunForm.populate()`
ограничивает список допустимых build'ов через
`Build.objects.filter(version_id=plan.product_version_id, is_active=True)`,
поэтому build другой версии даёт «Select a valid choice.»

## Автоматизация

Хотите, чтобы результаты CI-прогона попадали в Kiwi — добавьте шаг после тестов:

```yaml
- name: sync to Kiwi TCMS
  if: github.ref == 'refs/heads/main'
  run: |
    python3 infra/kiwi/sync.py --plan --results \
      --url "$KIWI_URL" --user "$KIWI_USER" --password "$KIWI_PASSWORD"
```

`--plan` в CI не нужен, если кейсы уже заведены: синк идемпотентен и без него,
но тогда новые тестовые классы не появятся. Учётные данные — в секретах CI,
не в репозитории.

## Прямые запросы к API

```python
import sys; sys.path.insert(0, 'infra/kiwi')
from kiwi_client import KiwiClient

c = KiwiClient().check_alive()
for product in c.get_products():
    print(product['id'], product['name'])
```

Стенд намеренно локальный: открытая регистрация, пароль по умолчанию `kiwi`,
`SECURE_SSL_REDIRECT` выключен. Для любого внешнего окружения всё это нужно
закрыть — см. `local_settings.py` и `docker-compose.yml`.
