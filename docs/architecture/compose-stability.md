# Compose stability

How this project keeps the Compose compiler from recomposing things that did not
change, and where the decisions are written down.

## What the compiler decides

For every parameter of every `@Composable`, the Compose compiler picks one of
three classes:

| class | what it means | comparison |
|---|---|---|
| `stable` | the type is known to be immutable | `equals` — the value is compared by content |
| `unstable` | the type is known to be mutable | `===` — only the same instance skips |
| *runtime* | the compiler cannot decide at compile time | `equals` by default; `===` when the caller reports an instance change |

Strong skipping is on by default (Kotlin 2.4.10), so the comparison is
inserted for every parameter. The only question is which one.

The three cases were measured against the generated bytecode of this project,
not read off the documentation — see
`docs/decisions/2026-10-22-compose-stability-contract.md`. The short version:
a *stable* parameter is compared with `Composer.changed`, an *unstable* one
with `Composer.changedInstance`, and a *runtime* one with a branch that
picks between the two at runtime.

An interface is a type the compiler cannot reason about: `List`, `Set`, `Map`
and `Collection` are always runtime-unstable. So is a class the compiler
cannot see the body of — `kotlinx.datetime.LocalDate`, `kotlin.time.Instant`
and every other final class that arrives from another module without a
stability marker of its own. These are not value classes: `LocalDate` wraps a
`java.time.LocalDate`, `Instant` wraps a `Long` and an `Int`.

A value class is different: it is inlined into its use, so the compiler sees
through it to the type underneath. The identifiers of this project —
`TaskId`, `NoteId` — are value classes over a `String`, and the compiler sees
the `String`, which is stable. They needed no entry in the contract, and the
measurement says so.

A **data class with only `val` properties** is stable, provided its property
types are stable too. `Task` is not: it holds a `List<TagId>` and a
`Set<TaskId>`.

A class the compiler cannot see the body of is **not** stable: it cannot prove
the properties are immutable, and it will not assume they are. That is the case
for every domain model read from another module — which is why `Task` needed an
entry in the contract rather than a local annotation.

The compiler records its verdict in the class file (`Task.$stable`) and the
call site hands that verdict to the composable it calls. The contract is what
makes the verdict say *stable*, and because the verdict travels inside the
compiled class, the contract has to be applied where the type is **declared**
as well as where it is used.

## Where the decisions live

- `config/compose/stability_config.conf` — the types the compiler is told are
  stable. Read by `shared` and `desktopApp` through
  `composeCompiler.stabilityConfigurationFiles`.
- `config/compose/stability_debt_baseline.conf` — the recorded size of the
  register of debt. The gate fails when the register and the record disagree,
  in either direction.
- `docs/decisions/2026-10-22-compose-stability-contract.md` — why it is a file,
  and what was measured.
- `scripts/check-compose-stability-config.py` — the gate: the contract names
  types that exist, the modules read it, the types it names keep the promise
  it makes for them, and the register of debt still matches the repository.
  An entry may name a **class** or an **interface** — the compiler honours an
  interface entry, and the promise it makes is about the *instances* of that
  type: an instance may be any of the types below it, so the gate checks those
  too, and holds them to the same promise. An `object` is stable without the
  contract, and a `typealias` resolves to no class: both are findings,
  because both say less than they appear to.

## The rule that decides everything

**The leaf is stable. The screen is not.**

A stable parameter is compared by `equals`, and `equals` over a collection is a
deep walk over every element. That is cheap for one task's tags and expensive
for a month of calendar entries. So:

- A **row** takes a stable item (`Task`, `Note`, `Project`) and compares it by
  content. One item's worth of comparison, bounded.
- A **section** takes a persistent collection (`ImmutableList`) and is compared
  as a section.
- A **screen state** is compared by identity. `AgendaUiState.Loaded`,
  `CalendarUiState.Loaded`, `TaskDetailUiState.Loaded`,
  `ProjectsUiState.Content` and `ProjectDetailUiState.Content` carry no
  `@Immutable` on purpose: the body of a screen is cheap to re-run, and a deep
  comparison of the whole screen is not.

## Writing a new composable

1. **Is the parameter a domain model?** It should be in the stability contract
   if it is a `val`-only data class that is rebuilt on every read **and the
   compiler would judge it unstable** — the contract promotes an unstable type
   to stable, and a type the compiler already judges stable needs no entry.
   The gate will tell you if the name does not resolve, and it will tell you
   if the type you named does not keep the promise: a `var` or a mutable
   collection in a contract type is a finding.

   "The compiler would judge it unstable" has an exact reading, and the
   stability report is where to read it. The compiler prints a parameter in one
   of three ways:

   - `stable` — the compiler knows the type is stable;
   - `unstable` — the compiler knows it is not;
   - no marker at all — the compiler cannot judge it at compile time. That is
     either a runtime judgement (a type of this project: the contract promotes
     exactly those) or a type whose body the compiler cannot see (a library
     type: the contract does not cover those, and there is nothing to add).

   A parameter the report prints with the `stable` marker needs no entry at
   all.
2. **Is the parameter a collection?** Declare it `ImmutableList` /
   `ImmutableSet` / `ImmutableMap` and build it at the boundary with
   `toImmutableList()` / `toImmutableSet()`. The detekt rule
   `NoUnstableCollectionParam` rejects a raw `List` / `Set` / `Map` /
   `Collection` parameter of a `@Composable`.

   The boundary is the **state that holds the value**, not the call of the
   composable. A collection rebuilt in the call is rebuilt on every
   recomposition — the promise of stability has to start where the value
   changes, not where it is handed over. So the screen state holds the
   persistent collection, and the composable receives it as it is.
3. **Is the parameter a screen state?** Pass it as `State` and read it with
   `collectAsStateWithLifecycle`; the composable that receives the value
   should be a leaf, so that the leaf is what skips.
4. **Is the parameter a callback, a navigator, a repository or a port?** Those
   are long-lived singletons: identity is the correct comparison, and they are
   runtime-unstable on purpose.

## Measuring

```bash
./gw :shared:compileKotlinJvm -PcomposeStabilityReport=true
```

writes `shared/build/compose_compiler_reports/jvm/`. Two files matter:

- `…-composables.txt` — one entry per composable, with each parameter's class.
- `…-classes.txt` — one entry per class, with the reason it is not stable.

The property forces the compilation to re-run: a report that was not
regenerated reads as a measurement of the current code and is not one.

The report is an **instrument, not a gate**. It exists only when a compilation
ran, the jvm and android compilations write the same file names, and the
directory is git-ignored — nothing in CI may depend on it.

## The known debt

`ComposeCollectionExemptions.kt` lists the composables that still take a raw
collection, and under each of them the parameters that still carry one. It is a
register of debt, not an allowance, and it is read from both sides:

- the detekt rule `NoUnstableCollectionParam` compares the code that is there
  with the register — and the register is handed to the rule as a parameter
  rather than read from a global: a raw collection parameter the register does
  **not** name is a finding, even when the composable itself is a known site,
  and a registered parameter whose declared type no longer matches the register
  is a finding too — that is what happens when a debt is paid;
- the gate `scripts/check-compose-stability-config.py` compares the register
  with the repository: a registered site that no source declares any more is a
  finding, and so is a registered parameter that no declaration of that site
  has.

Neither can do the other's job. The rule sees exact types and exact
parameters; the gate sees the whole tree, including the overloads that live in
different files and the composables that were deleted.

The **size** of the register is written down too, in
`config/compose/stability_debt_baseline.conf`, and the gate compares it with
the register: the debt may not grow without somebody deciding to raise the
bar, and a shrink has to be recorded. The number everyone quotes therefore
cannot drift away from the register it describes.

Converting one means: the parameter becomes `ImmutableList` / `ImmutableSet` /
`ImmutableMap`, the value is built at the boundary with `toImmutableList()` /
`toImmutableSet()`, the entry is deleted from the register, and the recorded
size goes down by one. The boundary is the state that holds the value: a
collection rebuilt in the call of the composable is rebuilt on every
recomposition, and the promise of stability never starts.

**The debt is paid.** As of 2026-10-26 the register is empty: every
`@Composable` in the repository takes its collections from the persistent kind,
and the value is built at the boundary. The register stays as an empty map,
because the rule is given it — an empty register is what makes a *new* raw
collection parameter a finding, and the recorded size is `0`, which the gate
compares with a register that holds nothing. The debt was paid in waves, each
one with its own measurement of the compiler's report: the menu, the proposals
and the logbook; the project screens; the matched ranges; the task editor and
the task filters; the shared sheets and dialogs; the notes and the tags; the
calendar and the agenda; the chat and the attachments; the calendar sync, the
checklist, the pomodoro and the profiles; the search, the settings and the
statistics; and finally the onboarding tour, the navigation and the test
bridge.

Three rules guard the contract:

- `NoUnstableCollectionParam` — no raw collection parameter of a `@Composable`.
- `NoMutableCollectionCast` — no `as MutableList` / `as MutableSet` /
  `as MutableMap`. The compiler compares a stable value by `equals`, so a
  collection mutated after such a cast keeps comparing equal to its old
  contents, and the screen goes stale without an error.
- `NoFalseImmutable` — no `@Immutable` on a class that declares a `var` or a
  raw collection. The annotation is a promise the compiler cannot check, and a
  broken promise shows up as a screen that is one recomposition out of date.
  `@Stable` is deliberately not covered: a `@Stable` holder of observable
  state (`private var by mutableStateOf(...)`) is the ordinary pattern.

The two rules that ask "is this a raw collection?" share one list of names
(`RawCollectionTypes`), so they cannot end up disagreeing about it. It covers
the interfaces (`List`, `Set`, `Map`, `Collection`), the mutable spellings
(`MutableList`, `MutableSet`, `MutableMap`, `ArrayList`, `HashSet`, `HashMap`)
and `Array`. `Iterable` and `Sequence` are deliberately out: they are rare as
a parameter of a composable, and a rule that fires rarely is a rule people
turn off.

## The state holds the persistent kind

The three rules above look at the **parameter** of a composable, or at the
**type** the contract names. None of them looks at what a *state* holds — and
that is where the promise a screen makes about its own contents can break.

A screen that receives `ArchiveUiState` passes `NoUnstableCollectionParam`:
the parameter is a state, not a collection. But the state itself carries
`List<Task>`, and a state that holds a raw collection cannot promise that the
instance it holds will not change. The value was also built on the wrong side
of the boundary — the screen that renders it is where the collection was
assembled, instead of the state that owns it.

So there is a fourth rule, and it is a gate rather than a detekt rule:

- `scripts/check-screen-state-collections.py` — a screen state does not hold a
  raw collection.

A **screen state** is a state type of a feature: a declaration whose name ends
with `UiState` or `State` (`AgendaUiState`, `TaskChildrenState`), or a member
of such a hierarchy (`ArchiveUiState.Content`). The states of the core —
`SyncState`, `EphemeralState` — are the state of a repository and of a
settings bundle, not of a screen that renders them, and they are out of scope.

It is a gate and not a detekt rule because deciding that a declaration is a
screen state needs the whole tree: a state is not visited by any rule, it is a
*type* — a parameter of a composable, or a member of a sealed hierarchy.

`config/compose/screen_state_collection_debt.conf` is the register of the
states that still hold a raw collection, one entry per property, and it
records its own size — the ratchet. The debt may not grow without somebody
deciding to raise the bar, and a shrink has to be recorded, in the same commit
as the change to the register. The gate reads the register from both sides: a
raw collection the register does not name is a new debt, and a registered
entry the code no longer has is a debt that was paid whose record did not move
with it.

The debt is **27 properties** in ten feature areas, as of 2026-10-27. The
waves that pay it are separate pull requests, one area at a time, each with
its own measurement and its own lowering of the recorded size. See
`docs/decisions/2026-10-27-a-screen-state-does-not-hold-a-raw-collection.md`.
