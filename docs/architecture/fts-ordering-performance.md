# Стоимость упорядочивания в полнотекстовом поиске по заголовкам задач

Замер двери, которая предлагает заголовок задачи для ссылки. Документ отвечает
на вопрос, который код не отвечает сам: **сколько из цены этой двери — сам
поиск по индексу, а сколько — упорядочивание и материализация найденного**.

Процедура замера — `shared/src/jvmTest/kotlin/com/singularity/todo/feature/search/performance/FtsOrderingPerformanceHarness.kt`,
задача Gradle — `:shared:ftsOrderingPerf`. Датасеты — общий генератор из
[#3090] (`:import-cli generate`), он же проверяет лимит архива.

## Что измеряется

Дверь — `FtsDao.searchTaskTitles`: заголовки задач, чей заголовок
совпал с индексом, «первые двадцать, сначала самые недавно обновлённые».
Её читают пикер связанных задач и подсказки внутренних ссылок
(`SearchTextIndexImpl.recentTaskTitles`).

Замер снимает **три цены по отдельности**:

| цена | что это |
|---|---|
| поиск | сколько стоит найти совпавшие строки — сам FTS и джойн с таблицей задач |
| материализация | сколько стоит прочитать **всё** совпавшее множество, а не двадцать строк из него |
| упорядочивание | сколько стоит отсортировать найденное |

Это разные вещи, и их нельзя увидеть в одной цифре: «дверь стоит 564 мс» не
сказывает, много ли из этих 564 мс съел индекс, а сколько — сортировка.
Поэтому замер идёт по цепочке вариантов, где каждый следующий — предыдущий
плюс одна вещь.

**Чего в замере нет.** Дверь читает две фазы в одной транзакции, чтобы обе
фазы видели один снимок базы (см. ADR). Harness меряет два оператора по
отдельности, и транзакция в его числах не стоит: ни `BEGIN`, ни `COMMIT` вокруг
пары не измерены. Снимок покупается ценой правильности, и это не та цена,
которую меряет этот документ.

### Варианты

Базовые, каждый — предыдущий плюс одна вещь:

| вариант | что это |
|---|---|
| `fts_match_count` | только FTS-таблица: `count(*)` по `MATCH` — чистая цена совпадения |
| `match_count` | тот же счёт по джойну с фильтром владельца — сколько стоит присоединить таблицу задач |
| `match_limit_no_order` | те же строки с лимитом продакшена, без упорядочивания |
| `match_order` | то же с `ORDER BY updated_at DESC` — как упорядочивание платит продакшен |
| `match_all_no_order` | **всё** совпавшее множество, без упорядочивания и без лимита — цена материализации |
| `match_all_order` | то же множество с `ORDER BY updated_at DESC` — цена упорядочивания |
| `current_ids` | продакшен-оператор, но выбирающий один только id |
| `current_no_offsets` | продакшен-оператор без позиций совпадения (строка задачи на месте) |
| `current_offsets_only` | продакшен-оператор, но вместо строки задачи — один id (позиции на месте) |
| `current` | продакшен-оператор дословно: вся строка задачи **и** позиции совпадения |

Все четыре оператора джойна записаны с `CROSS JOIN` — это прибивает порядок
джойна, и разница между парой операторов — это ровно то, чем они отличаются,
а не смена плана. План проверяется: у упорядоченного оператора есть ровно один
дополнительный шаг — временное B-дерево сортировки, — а остальные шаги
совпадают. `current_no_order` — продакшен-оператор без `ORDER BY`: он
записывается только как план и никогда не исполняется, это форма, которую
выбирает планировщик, когда его не ограничивают.

**Почему нужны обе пары.** Ограниченная пара (`match_limit_no_order` против
`match_order`) меряет упорядочивание **так, как его платит продакшен**, и
разница между ней — это не только сортировка: без `ORDER BY` SQLite
останавливается на двадцати совпадениях, а с `ORDER BY` он обязан обойти всё
совпавшее множество, чтобы знать, какие двадцать идут первыми, — и вычисляет
ключ сортировки для каждой совпавшей строки. Пара без лимита
(`match_all_no_order` против `match_all_order`) читает **всё** совпавшее
множество в обоих случаях, и разница между ними — цена сортировки и больше
ничего. Обе пары остаются в свипе: ограниченная — как мера продакшена,
неограниченная — как мера самой сортировки.

Кандидаты, измеренные после базовых:

| вариант | что это |
|---|---|
| `two_phase` | сначала порядок по id, потом чтение строк выживших по их id |
| `two_phase_flat_filters` | то же, но фильтр владельца записан условием на самой строке — план другой |
| `two_phase_tiebreak` | то же с темп-разделителем, который добавляет DAO |
| `two_phase_offsets` | то же, но позиции совпадения читаются обратно из индекса |
| `subquery_candidate` | то же одним оператором: упорядочивание в подзапросе |
| `current_with_index` | продакшен-оператор на схеме с `INDEX tasks(user_id, updated_at DESC)` |
| `index_candidate` | продакшен-оператор, переписанный так, что множество совпадений FTS — подзапрос, на той же схеме |

`current` — это оператор, которым DAO пользовался до правки, а
`two_phase_tiebreak` — оператор, которым он пользуется теперь. Оба измерены
как есть, так что разница между ними — разница между двумя операторами, а не
между «до» и «после» из разных прогонов.

### Две картины восстановления

Восстановление выравнивает `updated_at`: `BackupImporter.applyRows` пишет
`updated_at = now` каждой строке, поэтому после восстановления все задачи
выглядят тронутыми в один момент. Дверь упорядочивает по `updated_at DESC` —
на восстановленных данных этот порядок ничего не значит, и порядок среди
равных timestamps задаёт то, как сортировщик SQLite разложил строки.

Поэтому harness меряет **две картины** одного и того же датасета:

| картина | что это |
|---|---|
| «как восстановлено» | состояние, которое оставляет штатное восстановление: у всех строк один и тот же `updated_at` |
| «порядок датасета» | тот же датасет, но в `updated_at` возвращён его собственный порядок (`created_at`) — состояние рабочей базы, где строки трогали по одной |

Третья картина — **«новые сначала»** (`updated_at = -created_at`) — это
проба на порядок: она отвечает на вопрос «дорого ли сортировать, когда данные
уже в нужном порядке», и отделяет цену *сортировки* от цены *доставки
строк в сортировщик*.

Выводы замера в картинах разные, и это главный результат: **картина
«порядок датасета» — рабочее состояние базы, и в ней правка выигрывает
примерно в шесть раз; картина «как восстановлено» — состояние сразу после
восстановления, и в ней темп-разделитель делает новый оператор дороже**
(об этом — в разделе «Где правка дороже»).

### Сценарии

| сценарий | запрос | что он проверяет |
|---|---|---|
| `rare-number` | номер второго-новейшей задачи | редкий термин: совпадений почти нет, сортировать нечего |
| `frequent-task` | `task` | частый термин: совпадают **все** строки, сортируется весь результат |
| `frequent-synthetic` | синтетический термин, встречающийся во всех строках | то же, но термин не встречается в тексте задачи как слово |

`frequent-task` — главный сценарий: `MATCH 'task*'` совпадает со всеми
строками датасета, и стоимость упорядочивания видна в полном объёме.
`frequent-synthetic` отвечает на вопрос «это стоимость слова `task` или
стоимость совпадения по всем строкам» — и отвечает «совпадения по всем
строкам»: цифры у двух сценариев совпадают.

Латентности записываются, но **не проверяются**: часы меряют машину, а машина
общая. Проверяются то, что от машины не зависит: число совпадений, число
выданных строк и план запроса.

## Как это запускается

Два шага: сначала датасет, потом замер. Датасет — файл вне репозитория,
поэтому он генерируется рядом с замером, а не коммитится.

```bash
# 1. датасет: общий генератор из #3090
./gw :import-cli:run --args="generate --profile 10k --seed 4242 \
    --output $PWD/build/perf/10k.zip"

# 2. замер: восстановление базы стандартным путём и обход двери
./gw :shared:ftsOrderingPerf -Pperf.archive=$PWD/build/perf/10k.zip \
    -Pperf.iterations=20 -Pperf.warmup=3
```

Путь к архиву — **абсолютный**: `:import-cli` разрешает относительный
`--output` относительно своего модуля.

Параметры замера:

| параметр | значение | чем задано |
|---|---|---|
| итерации | 20 | `-Pperf.iterations=20` (по умолчанию 10) |
| прогрев | 3 | `-Pperf.warmup=3` (по умолчанию 3) |
| перцентиль | nearest rank: `ceil(fraction × n)`-й элемент отсортированной выборки | `percentile()` в harness |
| владелец задач | `perf-owner` | `-Pperf.owner=<id>` (по умолчанию `perf-owner`) |
| куча JVM | 1536m | `testTaskHeap` в `shared/build.gradle.kts` — тот же бюджет, что и у тестов модуля |
| seed генератора | 4242 | аргумент `--seed` генератора |
| archive budget | 64 MiB | `ArchiveBudget.MAX_TOTAL_BYTES` |

Замер восстанавливает архив **штатным путём** (`BackupImporter` +
`JvmBackupCodec` + настоящая база Room на диске), поэтому в замер попадают
только профили, которые проходят стандартное восстановление и укладываются в
лимит архива.

### Датасеты

Три размера (10k / 50k / 100k задач), один seed (4242), профили генератора
`10k` / `50k` / `100k`.

### Порядок прогонов

Раунды замера **переплетены**: каждый раунд исполняет каждый вариант по
одному разу, в меняющемся порядке. Машина, которая загрузится посреди
свипа, замедлит все варианты одинаково. Без переплетения «медленный» вариант
просто оказался бы первым.

### Разбор: из чего складывается цена

**Совпадение дешёвое, присоединение — среднее, сортировка — умеренная, а
дорого — доставка строк в сортировщик.** На 100k в рабочей картине:

| шаг | цена | что прибавилось |
|---|---:|---|
| само совпадение (`fts_match_count`) | 8.2 мс | FTS ищет совпадения |
| плюс джойн с задачами и фильтр владельца (`match_count`) | 45.6 мс | обход таблицы задач по совпавшим |
| плюс чтение всех совпавших строк (`match_all_no_order`) | 63.8 мс | материал строк |
| плюс сортировка всего множества (`match_all_order`) | 109.4 мс | **сортировка: ~46 мс** |
| продакшен-оператор целиком (`current`) | 564.1 мс | **доставка payload'а: ~455 мс** |

То есть **сортировка множества совпадений стоит около 46 мс, а доставка того,
что сортировщик несёт, — около 455 мс**: десять раз больше. Сортировать
надо было всегда; дорого было то, **что** сортировали.

Носить приходится **всю строку задачи и позиции совпадения** — и нёс он их
для каждой из 100 000 совпавших строк, а не для двадцати, которые выживут
лимитом. Разложение это видно прямо (рабочая картина):

| что несёт сортировщик | 10k | 50k | 100k |
|---|---:|---:|---:|
| один id | 10.731 | 70.380 | 118.740 |
| строка задачи без позиций | 29.296 | 184.730 | 282.195 |
| id и позиции | 38.382 | 219.812 | 368.723 |
| строка задачи и позиции (то есть продакшен) | 55.325 | 340.300 | 564.090 |

Позиции совпадения стоят примерно столько же, сколько сама строка задачи, а
вместе они дают множитель **пять-шесть** к цене сортировки id. Лимит в
двадцать строк не помогает: лимит отбрасывает строки **после** того, как
сортировщик их пронёс.

В картине «как восстановлено» это разложение почти отсутствует: там
`current` (52.6 мс на 100k) и `current_ids` (56.5 мс) отличаются на единицы
процентов, а в рабочей картине — в 4.7 раза. То есть дорогая доставка
payload'а привязана к тому, что сортировке есть что переставлять; когда все
ключи сортировки одинаковы, переставлять нечего и payload почти не стоит. Это
ещё одна причина, по которой обе картины нужны: одна картина показала бы
либо «правка бесплатна», либо «правка дорога», и обе были бы неполными.

**Позиции на этой двери никто не читает.** `offsets(tasks_fts)` даёт позицию
слова внутри заголовка — её читают подсветка совпадений в поиске по задачам и
по заметкам, а дверь заголовков отдаёт `Task` целиком, и позиция в нём
теряется. FTS4 умеет отдать позицию только пока отвечает на `MATCH`, поэтому
забрать её обратно — значит прогнать по всему множеству совпадений ещё раз.
Это и видно: `two_phase_offsets` (то же, но позиции читаются обратно) стоит
47.5 мс на 10k, 274.6 мс на 50k и 516.3 мс на 100k — почти весь выигрыш
двухфазности съеден.

**Победил двухфазный вариант.** Порядок по id, потом чтение строк выживших по
их id: 9.384 мс против 55.325 мс на 10k, 54.344 мс против 340.300 мс на 50k
и 108.963 мс против 564.090 мс на 100k — **в 5.9, 6.3 и 5.2 раза**. Второе
чтение стоит копейки: план — `SEARCH t USING INDEX sqlite_autoindex_tasks_1
(id=?)`, читаются двадцать строк из ста тысяч. И видно, что двухфазный вариант
стоит примерно столько же, сколько сортировка всего множества (109.4 мс против
108.9 мс на 100k) — то есть он платит за сортировку и почти не платит за
остальное.

### Форма фильтра во второй фазе: план решает всё

Двухфазность покупается тем, что вторая фаза читает **двадцать строк по
первичному ключу**. Это свойство зависит не от текста запроса, а от **плана**,
который выбирает SQLite, — а план зависит от того, как записан фильтр
владельца.

Очевидная форма фильтра — условие на самой строке:

```sql
SELECT t.* FROM tasks t
WHERE t.id IN (:ids)
  AND t.user_id = :userId
  AND t.archived_at IS NULL
```

Планировщик выбирает для неё `index_tasks_user_id`: он идёт по индексу
владельца и у каждой его строки проверяет id. То есть чтение двадцати строк
превращается в обход **всех задач пользователя** — и растёт вместе с базой.
План это видно буквально:

```
- read the rows with the filters on the row:
- SEARCH t USING INDEX index_tasks_user_id (user_id=?)
```

Форма, которую теперь пишет DAO, — та же проверка, но **связанная**: та же
строка ищется по своему id, и уже она проверяется на владельца и на архив:

```sql
SELECT t.* FROM tasks t
WHERE t.id IN (:ids)
  AND EXISTS (
    SELECT 1 FROM tasks o
    WHERE o.id = t.id
      AND o.user_id = :userId
      AND o.archived_at IS NULL
  )
```

План:

```
- read the rows:
- SEARCH t USING INDEX sqlite_autoindex_tasks_1 (id=?)
- CORRELATED SCALAR SUBQUERY 1
- SEARCH o USING INDEX sqlite_autoindex_tasks_1 (id=?)
```

Первичный ключ остаётся **единственным** способом найти строку, поэтому
SQLite читает ровно двадцать строк, а проверка владения и архивного состояния
по-прежнему происходит в базе, для каждой прочитанной строки. Обе формы
отвечают на один и тот же вопрос и читают одни и те же строки — но это
разные операторы для планировщика, и цена у них разная.

Цена этой разницы (вариант `two_phase_flat_filters` — та же вторая фаза, но с
условием на строке):

| картина | 10k | 50k | 100k |
|---|---:|---:|---:|
| «порядок датасета» | 13.144 / 10.374 | 68.531 / 61.027 | **170.768 / 81.426** |
| «как восстановлено» | 18.771 / 9.073 | 63.138 / 30.689 | **111.442 / 53.810** |
| «новые сначала» | 11.125 / 6.600 | 64.840 / 34.300 | **113.548 / 52.669** |

(формат: с условием на строке / так, как в DAO)

На 100k разница — вдвое, и она растёт с базой: обход задач пользователя
растёт вместе с числом его задач, а чтение по первичному ключу — нет. Это
и есть причина, по которой форма второй фазы — не стилистический выбор: без
неё двухфазность теряет смысл именно там, где она нужна, на большой базе.

**Индекс не помог.** `INDEX tasks(user_id, updated_at DESC)` меняет план на
тот, который для редкого термина обходится **на четыре порядка дороже**: на
100k в рабочей картине — 12 947 мс с индексом против 0.436 мс без него, а
в картине «как восстановлено» — 5.0 секунды. Причина — план, а не сам
индекс: с индексом SQLite идёт по нему и для каждой строки проверяет
`MATCH`, то есть вычисляет совпадение построчно, вместо того чтобы один раз
пройти по готовому списку совпадений. `index_candidate` (тот же индекс, но
запрос переписан так, что множество совпадений FTS — подзапрос) это чинит —
и стоит 13.1 мс на 100k для редкого термина, — но для частого термина он
всё равно проигрывает двухфазному варианту (306.2 мс против 109.0 мс), а для
редкого — проигрывает простому оператору (13.1 мс против 0.436 мс). Индекс в
схему не добавлен.

### Где правка дороже: картина «как восстановлено»

Здесь новый оператор **дороже** старого: 13.357 мс против 8.587 мс на 10k,
63.532 мс против 34.047 мс на 50k и 104.112 мс против 52.602 мс на 100k — в
1.6, 1.9 и 2.0 раза. Причина — темп-разделитель
`ORDER BY t.updated_at DESC, t.rowid DESC`.

Когда у всех строк **один и тот же** `updated_at`, первый ключ сортировки
ничего не различает, и весь порядок задаёт второй. Старый оператор в этой
картине сортировал по одному ключу, который у всех строк одинаков; новый
сортирует по двум, и второй ключ делает настоящую работу — переставляет
десять тысяч, пятьдесят тысяч, сто тысяч строк. В картине «порядок
датасета» первый ключ и так различает строки, и там темп-разделитель почти
ничего не стоит (108.963 мс против 81.426 мс на 100k).

Цена темп-разделителя в картине восстановления — 4.3 мс на 10k, 32.8 мс на
50k и 50.3 мс на 100k.

Это цена **правила**. Старый порядок среди задач, обновлённых в один момент,
был не правилом, а тем, как сортировщик SQLite разложил строки, — то есть
порядком байтов строк. Новый порядок — правило: среди задач, обновлённых в
один момент, первой идёт вставленная последней. И на восстановленной базе
(где `updated_at` у всех строк одинаков) это правило вдобавок превращает
«произвольные двадцать из ста тысяч» в «двадцать последних вставленных» —
то есть в осмысленный ответ.

Цена этого правила — десятки миллисекунд на самом большом датасете и только
в той картине, где `updated_at` у всех строк одинаков; в рабочей картине она
около нуля. Это единственное место, где правка медленнее старого кода, и в
этом месте новый ответ к тому же времени детерминирован, а старый — нет.

### Что осталось за рамками правки

**Дверь заметок не тронута.** `searchNoteTitlesByMatch` устроена так же и
несёт те же позиции совпадения через ту же сортировку. Она не измерялась:
задача [#3199] — про базы задач, и правило «правка остаётся в подтверждённом
узком месте» запрещает менять соседнюю дверь по аналогии. Это follow-up с
собственным замером.

**Позиции совпадения в поиске по задачам и заметкам не тронуты.** Там они
читаются — их показывает подсветка, — и стоимость их получения настоящая.
Правка их не касается.

**Сортировка множества совпадений осталась.** 109.4 мс на 100k в рабочей
картине — это цена `ORDER BY updated_at DESC` над ста тысячами совпадений
(`match_all_order`), и она не связана с тем, что именно несёт сортировщик.
Убрать её можно было бы только сменой схемы или переписыванием индекса, а
задача [#3199] запрещает менять схему FTS и требует для этого доказательства
измерением.

**Индекс `tasks(user_id, updated_at DESC)` не добавлен.** Измерение показало,
что он меняет план на худший для редких терминов и в лучшем случае
проигрывает двухфазному чтению. Добавление индекса без доказательства
измерением запрещено задачей.

**Путь «Related Tasks» целиком не переписывался.** Замер снимает DAO-запрос
двери заголовков отдельно от пути пикера: путь пикера измерен в
`docs/architecture/related-task-picker-performance.md`, и правка [#2981] его
уже сократила.

## Наблюдения о данных

**Восстановление выравнивает `updated_at`.** `BackupImporter.applyRows` пишет
`updated_at = now` для каждой строки, поэтому после восстановления все задачи
выглядят тронутыми в один момент, а порядок двери (`ORDER BY updated_at
DESC`) на восстановленных данных ничего не значит. Код восстановления не
менялся — это осталось наблюдением, — но harness меряет обе картины.

**Частый термин совпадает со всеми строками.** `MATCH 'task*'` на датасете
задач совпадает со всеми строками: у каждой задачи в заголовке есть слово
`task`. Это и делает сценарий `frequent-task` показательным — он меряет
худший случай: сортируется весь результат, а не двадцать строк из него.

**Лимит не спасает.** `LIMIT 20` стоит после `ORDER BY`: сортировщик сначала
проносит всё совпавшее через сортировку и только потом отбрасывает лишнее.
Это видно в `match_limit_no_order` (3.9 мс на 100k — SQLite останавливается
на двадцати совпадениях) против `match_order` (108.7 мс — сортируются все
сто тысяч).

**Лимит не отсекает и работы сортировки.** Чтобы знать, какие двадцать строк
идут первыми, SQLite обязан вычислить ключ сортировки для каждой совпавшей
строки, поэтому ограниченный оператор всё равно обходит всё множество — и
именно поэтому разница между `match_limit_no_order` и `match_order` не есть
цена сортировки. Цена сортировки — это разница между `match_all_no_order`
(63.8 мс) и `match_all_order` (109.4 мс) на 100k: обе стороны читают всё
множество, различается только порядок.

## Воспроизводимость

Замеры сняты на одной машине, seed генератора 4242, 20 итераций после 3
прогревов, p50 и p95 — **nearest rank** по выборке итераций:
`ceil(fraction × n)`-й элемент отсортированного списка, без интерполяции.
Раунды переплетены (см. «Порядок прогонов»). Сырые логи прогонов лежат
рядом с замерами в `build/diagnostics/sweep4-10k.log`,
`build/diagnostics/sweep4-50k.log`, `build/diagnostics/sweep4-100k.log` — это
рабочий каталог, в репозиторий они не попадают; таблицы выше переносят их
числа.

Команда повторяет замер целиком:

```bash
for profile in 10k 50k 100k; do
  ./gw :import-cli:run --args="generate --profile $profile --seed 4242 \
      --output $PWD/build/perf/$profile.zip"
  ./gw :shared:ftsOrderingPerf -Pperf.archive="$PWD/build/perf/$profile.zip" \
      -Pperf.iterations=20 -Pperf.warmup=3
done
```

Латентности на общей машине разбросаются: соседний процесс и другая сессия
двигают числа. Поэтому выводы замера опираются не на отдельные цифры, а на
**отношения** вариантов, снятых в одном переплетённом свипе: `current`
проигрывает `two_phase_tiebreak` в 5.9, 6.3 и 5.2 раза в одной и той же
серии замеров, а не «стало 55 мс — стало 9 мс» из разных прогонов. Разброс
на общей машине виден и по p95: на 100k в рабочей картине `current` стоит
564.1 мс по p50 и 1230.2 мс по p95, а `two_phase_tiebreak` — 109.0 мс и
263.9 мс; порядок величин один и тот же.
