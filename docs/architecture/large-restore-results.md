# Результаты проверки восстановления больших датасетов (профили `10k` и `50k`)

Замеры настоящего прогона на устройстве. Сама процедура — `scripts/verify-large-restore.py`,
её устройство, команды и правила описаны в `docs/architecture/verification.md`. Этот документ
отвечает на вопрос, который процедура не отвечает сама: **что реально работает на устройстве
и где проходит настоящая верхняя граница**.

Первоисточники замеров лежат рядом, в `docs/architecture/large-restore-evidence/`: отчёты прогонов
(`profile-10k-report.json`, `profile-50k-report.json`), sidecar-манифесты генератора, с которыми
сверялись counts (`profile-10k-manifest.json`, `profile-50k-manifest.json`), логи Maestro
(`profile-10k-browse-flow.txt`, `profile-50k-browse-flow.txt`) — их пишет Maestro, а не команда,
поэтому пройденный flow виден по ним независимо от отчёта, и выдержка из `logcat` устройства
(`profile-50k-crash.txt`), по которой видно, где именно приложение исчерпало кучу.

## Устройство и сборка

| | |
|---|---|
| устройство | realme RMX3938, Android 15 (SDK 35), arm64-v8a, serial `0O65321F32204DD5` |
| сборка | debug APK `0.1.0+g37da3f26df1b`, package `com.singularity.todo` |
| вариант | debug (`DEBUGGABLE` в `dumpsys package`), `largeHeap` в манифесте **не запрошен** |
| куча устройства | `dalvik.vm.heapgrowthlimit=192m` (обычная куча), `dalvik.vm.heapsize=512m` |

Обе цифры кучи сняты с устройства (`getprop`), а не взяты из документации: именно 192 MiB —
предел, в который упирается профиль `50k`.

## Как прогонялось

```bash
python3 scripts/verify-large-restore.py \
  --serial 0O65321F32204DD5 --profile 10k --seed 42 --out build/large-restore-10k-round11
```

Профиль `50k` — тот же прогон с `--profile 50k`, seed тот же (42). Импорт идёт **только через
UI**: Settings → Backup → Restore → SAF-пикер → подтверждение. Единственная debug-ссылка в
процедуре — `todo-debug://seed?reset=content`, очистка профиля перед прогоном.

Порядок фаз: очистка профиля → архив сверх budget (должен быть отвергнут) → прерванный импорт
(должен оставить профиль пустым) → импорт → сверка counts и связей с sidecar-манифестом по
снятой с устройства базе → перезапуск приложения → UI-пути (список, деталь, поиск, Related Tasks).

Перед очисткой приложение обязано быть **поднято и показать свой список** (`nav_tab_inbox` в
`uiautomator dump`): холодный процесс читает зашифрованное хранилище сессии и узнаёт свою
идентичность через несколько секунд, и очистка, отправленная раньше, тихо не удаляет ничего.
С прогрева очистка видна по маркеру приложения в `logcat` и по времени: 5.2 s на пустом профиле
и 457.7 s на профиле с 10 000 задач.

## Измерения

| | профиль `10k` | профиль `50k` |
|---|---|---|
| архив на диске | 2 158 228 B | 6 496 280 B |
| распакованный | 13 871 747 B (13.2 MiB) | 48 208 143 B (46.0 MiB) |
| **время импорта** | **26.8 s** (тап подтверждения → snackbar) | **90.3 s** |
| размер БД на устройстве | 69 573 784 B (66.3 MiB) | 149 453 640 B (142.5 MiB) |
| память процесса | `TOTAL PSS: 298936` (swap PSS 22 763) | `TOTAL PSS: 415752` (swap PSS 129 997) |
| очистка профиля перед прогоном | 5.2 s (профиль был пуст) | 457.7 s (удалено 10 000 задач) |
| counts против манифеста | совпадают | совпадают |
| связи против состава архива | совпадают | совпадают |
| перезапуск, список/деталь/поиск/Related Tasks | **проходят** | **падают (OOM)** |

Время импорта — от тапа кнопки подтверждения до snackbar «Restore complete». Очистка профиля в
таблицу не входит: она упирается в запись в sync-outbox по одной строке на удалённую задачу и
к свойству импорта отношения не имеет.

### Counts

| entity | `10k` манифест / база | `50k` манифест / база |
|---|---|---|
| tasks | 10000 / 10000 | 50000 / 50000 |
| projects | 100 / 100 | 250 / 250 |
| tags | 100 / 100 | 120 / 120 |
| notes | 1000 / 1000 | 2000 / 2000 |
| checklistItems | 20000 / 20000 | 25000 / 25000 |
| taskDependencies | 1500 / 1500 | 5000 / 5000 |
| taskTags | 14814 / 14814 | 75257 / 75257 |
| subtasks | 2500 / 2500 | 12500 / 12500 |

`countProblems: []`, `linkProblems: []` и `linkIdentityProblems: []` в обоих профилях: не только
числа совпали, но и состав связей (задача↔проект, задача↔тег, чек-лист↔задача, заметка↔задача,
заметка↔проект, проект↔проект) совпал с архивом.

Counts сверяются **в пределах профиля**, а не всей базы: строки принадлежат профилю по
`user_id` (`scope`), и строки, висящие на задаче, считаются через её задачу. На этом устройстве
профиль один (`default`), поэтому числа совпадают и с построчным счётом всей базы.

Сверка идёт **до** UI-проверок. После неё база на устройстве перестаёт быть точной копией
архива: пикер Related Tasks по заданию прогона добавляет **одну** связь (`Task 10000` в профиле
`10k`, `Task 50000` в профиле `50k`), и она записана в отчёте как `uiPaths.pickerAddedRelation`.
Снятая после прогонов база (`device-db/`) содержит эту связь, и её нельзя читать как снимок
импорта без поправки на неё.

## Поведение на границах (проверено в обоих профилях)

* **Архив сверх budget** — приложение показывает диагностику отказа и **не пишет ничего**:
  после попытки все таблицы пусты.
* **Прерванный импорт** — профиль остаётся **пустым**: половины датасета не остаётся; либо
  импорт не начался, либо откатился целиком.

## Реальная верхняя граница

**Поддерживаемый профиль на этом устройстве — `10k`.** Граница проходит между `10k` и `50k`, и
ограничивает её **не архив, а куча приложения**.

* `50k` — **восстановление проходит целиком**: импорт 90.3 s, все counts и связи совпали с
  манифестом, данные переживают перезапуск приложения. Но **UI-пути не выдерживают**.

  Что именно ломается, видно по `logcat` устройства (`profile-50k-crash.txt`) и по логу flow
  (`profile-50k-browse-flow.txt`):

  1. Список открывается: `nav_tab_today` виден, вкладка Inbox открывается, строка задачи
     (`task_item_task_5`) видна и по ней можно тапнуть, related-задача (`Task 49995`) и кандидат
     пикера (`Task 50000`) читаются из базы.
  2. **Открыть деталь задачи нельзя.** Первое исчерпание кучи происходит в коде приложения — в
     наблюдателе тегов задачи, который деталь экранирует:

     ```
     Throwing OutOfMemoryError "Failed to allocate a 288 byte allocation with 25296 free bytes
     and 24KB until OOM, target footprint 201326592, growth limit 201326592; giving up on
     allocation because <1% of heap free after GC."
       at com.singularity.todo.core.database.TaskDao_Impl$observeTagCrossRefs$1.invokeSuspend(TaskDao_Impl.kt:6467)
     ```

     201326592 байт — это и есть `dalvik.vm.heapgrowthlimit=192m`; в логе видно
     `191MB/192MB, 0% free` после GC, то есть куча заполнена ещё до открытия детали.
  3. Процесс падает на главном потоке, пока читается дерево экрана:

     ```
     FATAL EXCEPTION: main
     java.lang.OutOfMemoryError: Failed to allocate a 80 byte allocation ...
       at androidx.compose.ui.node.LayoutNode.<init>(LayoutNode.kt:1611)
       at androidx.compose.ui.semantics.SemanticsOwnerKt.getAllUncoveredSemanticsNodesToIntObjectMap(SemanticsOwner.kt:363)
     ```

     Это обход дерева доступности Compose (`getAllUncoveredSemanticsNodesToIntObjectMap`), то
     есть разворачивание узлов всех 50 000 строк списка в семантику. Такой обход запускает
     автоматизация, читающая экран, — но он лишь добивает и без того исчерпанную кучу; первое
     OOM в пункте 2 от автоматизации не зависит.

  Итог: **виновата куча, а не restore**. Данные восстановлены целиком, список их показывает, а
  вот открыть деталь на таком объёме приложение не может.
* **archive budget (64 MiB) ограничивающим фактором не является**: распакованный архив `50k` —
  46.0 MiB, он в бюджет укладывается.
* `100k` **не заявляется**: на устройстве не гонялся, а распакованный архив ~62 MB при budget
  64 MiB упирался бы в лимит вторым образом.

Иными словами, граница упирается в отображение восстановленного датасета, а не в сам restore:
восстановление `50k` приложение осилило.

## Что не измерялось

* Профиль `100k` на устройстве не гонялся.
* Эмулятор (`emulator-5554`) в замеры не вошёл: под нагрузкой хоста меню приложения не
  успевало открыться, и замер получился бы не про восстановление.
* Устройство с `largeHeap` не измерялось: там картина будет другой (предел кучи 512 MiB).
* Граница между `10k` и `50k` не сужена: генератор отдаёт именованные профили `1k`/`10k`/`50k`/
  `100k`, и промежуточного профиля у него нет.
* Не измерено, сколько именно памяти съедает список из 50 000 задач: приложение падает, а не
  рапортует, поэтому отделить «список» от «детали» по цифрам нельзя — видно только, что первое
  OOM приходится на деталь.

<https://github.com/gazon1/sing/issues/3091#issuecomment-7093699395>.
