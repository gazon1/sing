# Проверка правки: как убедиться, что код собирается и проходит гейты

> **Reference, не процедура.** Этот документ отвечает на один вопрос: *чем и в каком
> порядке проверять правку в этом репозитории*. Порядок команд, цена запусков и
> причины за каждым решением — здесь; что именно проверяет CI — в
> `docs/architecture/ci.md`, как писать сами тесты — в `docs/architecture/tests.md`.

## Чем собирать: `./gw`, а не `./gradlew`

Параллельные worktree делят `~/.gradle`, а делённый Gradle Home — это общий лок кэша
и общий реестр демонов: сборка толкается с соседями и идёт в разы дольше. `./gw`
даёт worktree приватный `GRADLE_USER_HOME` (кеши и JDK остаются общими — их не пишут
одновременно). На машине с несколькими checkout'ами это разница между 5 и 40 минутами.

Два Gradle-вызова одновременно не запускай: блокируется общий кэш, и падает не та
сборка, которую ждут.

## Карта команд

```bash
just gate         # ВСЕ гейты: check.sh → detekt → agenda-флоу (SKIP_MAESTRO=1 — без flows)
./check.sh                    # реестр гейтов + тесты + Android + detekt
bash scripts/ci/static-gates.sh   # ТОЛЬКО скриптовые гейты (≈1 мин, без JVM)
just tests::impact    # тесты, которые эта правка может сломать (карта по дереву)
./gw :shared:jvmTest     # быстрый цикл (без популяции = только fast)
./gw :shared:jvmTest -Ptest.population=full   # полный набор, как в CI
./gw :shared:jvmTest -Ptest.tags=slow:migration   # одна категория медленных
./gw :androidApp:assembleDebug   # Android
./gw :desktopApp:run      # Desktop (xvfb-run -a)
./gw :desktopApp:test     # Desktop UI tests (задача `test`, не `jvmTest`)
./gw :shared:exportToolSurface   # перегенерировать config/docs/tool-surface.json

just lint        # detekt (все модули с baseline), enforcing
just detekt-fix  # auto-fix detekt + ktlint in-place

python3 scripts/detekt-summary.py   # находки detekt по правилам, а не XML дампом
```

`just <recipe> name=value` **не** работает (just 1.57.0: `tags=agenda` парсится как
env var, не как параметр). Используй позиционную форму: `just gma` (алиас для
`gm agenda`).

**Карта затронутых тестов — `just tests::impact`.** Ответ на вопрос «что эта правка
ломает?» считается по дереву, а не выдумывается: правка в области тянет тесты этой
области, правка в классе тянет тесты, которые этот класс упоминают, изменённый тест
тянет сам себя. Это **кандидаты**, а не вердикт: карта никогда не говорит «вне карты
безопасно» — она говорит, что стоит прогнать первым.

## Порядок detekt

Сначала `:shared:detekt` — там почти весь код, и замечание там останавливает проверку
через две минуты, а не через четыре модуля:

```bash
./gw :shared:detekt                                  # сначала — 90% кода
./gw :desktopApp:detekt :androidApp:detekt :mcp-server:detekt   # потом остальные
```

## Компилируй сразу после связной правки

Правка, которая тянет за собой соседний файл (сигнатура, интерфейс, DI-биндинг),
проверяется компиляцией в ту же минуту: `./gw :shared:compileKotlinJvm` (для тестов —
`:shared:jvmTestClasses`). Открытие полного прогона на сломанной компиляции стоит
сорока минут ожидания, и диагностика «упало в тестах» уводит не туда: компиляция падает
раньше и падает другой строкой.

## Долгий запуск — одна фоновая задача и один ожидатель

Запусти в фоне, пиши лог в уникальный файл и дальше жди уведомления о завершении;
читай вывод, когда задача завершилась, а не по таймеру. Формулировка «проверяй по
необходимости» — приглашение поллить, и у него нет критерия завершения: в одной сессии
211 из 314 tool-вызовов были просмотрами состояния (39 % — `task_output`, остальное —
опросы в bash), а полезной работы было 103 вызова.

Сколько именно ждать — берётся из измерения (`docs/testing/gate-costs.md`), а не из
догадки: прогон, который стоит 37 минут, не «проверяется» через 30 секунд — это десять
раундов контекста впустую.

Формы ожидания:

```bash
sgate run-all --summary              # сводка: по строке на упавший гейт
sgate run-all                        # полный отчёт (таблица + панели)
sgate run-all --gate "write tool"    # один гейт по имени
./wait-for <log> <паттерн>           # ждёт строку в логе и печатает хвост один раз
```

`./wait-for` печатает хвост **один раз** (код 0 — нашлась, 1 — таймаут, 2 — неверные
аргументы). Опрос циклом — это тот же ждёшь, только дороже. Лог, который нужен потом,
пиши в файл с уникальным именем (`build/diagnostics/<что>-<метка>.log`), а не перетирай
общий.

## Гейтовый venv принадлежит checkout'у

`sgate` — editable-установка `scripts/src/`, поэтому венв, поставленный в другом
worktree, меряет *тот* checkout: гейт зелёный, а проверял он чужое дерево.
`bash scripts/ci/preflight-gate-tools.sh` печатает, чей это checkout (строка `sgate`;
`FOREIGN` — не тот). Свой венв на checkout:

```bash
SINGULARITY_TOOLS_VENV="$HOME/.venvs/singularity-todo-$(basename "$PWD")" \
    bash scripts/ci/setup-local-tools.sh
export PATH="$HOME/.venvs/singularity-todo-$(basename "$PWD")/bin:$PATH"
```

Инструменты гейтов ставятся, а не подкладываются в `PYTHONPATH`: юнит-тесты гейтов
запускают их с минимальным окружением (`env={'PATH': ...}`), и пакет, видимый только
через `PYTHONPATH`, для них невидим.

## Хост бывает занят

Параллельно на машине могут крутиться Gradle других сессий — они делят CPU, RAM и
Gradle home, но не `shared/build`. Полный `:shared:jvmTest -Ptest.tags=fast,slow` в
таком случае идёт час вместо получаса, и таймаут-тесты (`CoroutineDiagnosticsTest`)
флейкают от нагрузки, а не от кода.

Спроси у хоста, а не у памяти: `./sg host-load` (или `--json`). Порог — **2.0 на ядро**,
измерено: на 16 ядрах load 16 (1.0/ядро) даёт `:shared:jvmTest` за 8 минут, load 42–52
(2.6–3.2/ядро) — за 24. Занят → целевой набор (`--tests`) или ждать; полный прогон —
когда целевой зелёный.

## Находки detekt — одним файлом

`shared/build/reports/detekt/detekt.xml` (путь, строка, правило) — консоль Gradle даёт
только счётчик. **Правило и его подоплёка — в комментариях `config/detekt/detekt.yml`**:
там, почему порог такой; кастомные правила — в `detekt-rules/` (напр.
`NoDroppedUiStateProperty`: свойство состояния — обязательный параметр **каждого**
варианта, дефолт запрещён). `ClassSignature` — сигнатура data class, влезающая в строку,
пишется в одну строку (ADR `2026-10-09-detekt-class-signature-gotcha`).

Отчёт detekt — это XML на находку. `scripts/detekt-summary.py` печатает то же самое по
правилам и местам в два-три экрана; выгружать `detekt.xml` целиком в контекст — это
сотни строк ради ответа, который помещается в первые двадцать.

## Покрытие и floors

**Floor покрытия приложения живёт в `settings.gradle.kts`.** Блок `kover { }` в
корневом `build-скрипте` инертен: у корневого проекта нет своего Kover-расширения, и
`plugins.withId("…kover") { … }` там не выполняется никогда (проверено `println`-зондом).
Правила читаются из settings-level `kover { reports { verify { } } }`. Гейт
`coverage floor declaration` (`scripts/check-coverage-floor-declaration.py`) не даёт
объявлению вернуться в мёртвое место, а `coverage task list` следит, чтобы в измерение
попадал каждый модуль, чьи классы в знаменателе.

Проверка floors в прогоне: `:koverVerify` (INSTRUCTION/BRANCH/LINE покрытие
`com.singularity.todo.*` ниже floor 27/20/27).

Отчёты покрытия: `just coverage` (агрегированный XML), `just coverage-html`,
`just coverage-markdown`. Матрица «что чем покрыто» — `docs/testing/coverage-matrix.md`.

## Пуш в ветку PR — без `--no-verify`

`pre-push` hook (`.githooks/pre-push`) проверяет **пушимое дерево**: структурные гейты
+ `detekt --auto-correct` (сам чинит большую часть находок). Пропуск хука отправляет ту
же находку в CI — минуты вместо получаса. `--no-verify` — только для WIP-коммитов.

Pre-push несёт и правила дерева (на пушимое дерево, не на рабочее): указатели `AGENTS.md`
(`scripts/check-agents-pointers.py`), запись реестра ченджа (`scripts/check-issue-registry.py`),
вердикт ревью ченджа (`scripts/check-review-verdicts.py`). Всё вместе — меньше двух
секунд; полный сьют гейтов в хук не входит намеренно (1 м 17 с, и две трети его — гейты,
которые обязаны прогонять всё).

**SSH keepalive.** Git открывает соединение с GitHub *до* хука, и пока хук крутит detekt
(несколько минут), соединение простаивает: GitHub закрывает его, и пуш падает с 141,
хотя хук только что напечатал `=== Pre-push OK ===`. `just setup-hooks` ставит
`core.sshCommand` (`ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=10`) один раз
для репозитория — он безопасен для всех worktree'ов.

## Окружение без дисплея

`xvfb-run` есть не везде: `:desktopApp:test` идёт без дисплея, а `:desktopApp:run` — GUI,
и ему нужен X-сервер (`xvfb-run -a ./gw :desktopApp:run`). Если `xvfb-run` не установлен,
это не повод пропускать тесты — они headless.

## Производные файлы

**Каталог инструментов — производный файл.** `config/docs/tool-surface.json` читает
MCP-сервер и агент; он генерируется (`./gw :shared:exportToolSurface`) и проверяется
гейтом. Меняешь схему или описание инструмента — перегенерируй сразу, иначе гейт скажет,
что каталог устарел, а не что ты изменил.
