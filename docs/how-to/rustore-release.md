# Публикация в RuStore — первая версия и последующие релизы

Операционная процедура для магазина RuStore: что загружать, чем заполнять карточку,
кто и что делает вручную, что делает API, и какие идентификаторы нужны CI.

Состояние на 2026-11-19: приложение создано, первая активная версия **не опубликована** —
модерация и публикация делаются человеком в Console (п. 5). Релиз `v0.2.2`, который
грузят в магазин, собран и подписан; идентификаторы и его проверенные значения — в
п. 1 и п. 2.

> Требования RuStore к иконке, скриншотам, возрастной категории и data-safety взяты
> из справки RuStore. Повторно сверить их с первоисточником во время правки не
> удалось (сайт отдавал WAF-ошибку 429), поэтому формулировки ниже — «по справке»,
> а поля нужно сверять по самому Console при заполнении.

## 1. Идентификаторы

| Что | Значение | Откуда |
|---|---|---|
| RuStore application ID | `2063789931` | `GET /public/v1/application` |
| company ID (разработчик) | `2351561732` | там же |
| Package name | `com.singularity.todo` | `androidApp/build.gradle.kts` |
| Платформа / устройство | `ANDROID` / `MOBILE` | RuStore API, `GET /public/v1/application` |
| Статус приложения | `NOT_PUBLISHED`, `versionCode: 0` | там же |
| Имя приложения в Console | `" sing"` — с ведущим пробелом | там же, поле `appName` |
| Ключ API | `keyId` пользователя (`RUSTORE_KEY_ID`); секрет в `RUSTORE_KEY` | RuStore Console → API |
| Версия, которая станет активной | `0.2.2`, versionCode `2002` (релиз `v0.2.2`) | п. 2; подтверждается в Console после публикации |

Активный `versionCode` в приложении появится только после первой публикации: до неё
RuStore отдаёт `versionCode: 0`. Значение, которое #3001 читает из Console, — `2002`;
сверень его в Console после публикации и, если RuStore присвоил другой, поправь
эту строку.

Идентификаторы нужны дальше: #3000 (публикация через API) и #3001 (CI-интеграция)
обращаются к RuStore по `appId`/`packageName`, а не по имени.

`keyId` ключа API — **не** то же самое, что `appId` приложения или `companyId`
разработчика: это идентификатор ключа в профиле пользователя RuStore. Он выдаётся
Console вместе с приватным ключом и ничего не говорит о приложении.

Имя `" sing"` надо поправить в Console до подачи на модерацию: с ведущим пробелом
так оно и будет на карточке.

## 2. Что именно грузим

**В магазин идёт релиз `v0.2.2`, а не `v0.2.1`** (почему — в п. 8). Таблица ниже
описывает проверенный предыдущий артефакт: по нему сверяются формат, размер и
fingerprint сертификата. Сам загружаемый APK — артефакт джоба `release.yml` для тега
`v0.2.2` (versionCode `2002`), его SHA-256 берётся из лога релиза.

| Что | Значение |
|---|---|
| Тег релиза | `v0.2.1` (draft-релиз GitHub) — справочно, в магазин не грузится |
| versionName / versionCode | `0.2.1` / `2001` |
| APK | `singularity-0.2.1-android.apk`, 33 968 011 байт |
| SHA-256 APK | `a9ac21a5f0299ec5910431981b028e8e798bfa524a11c51a5016e641d032ea07` |
| Сертификат (SHA-256) | `102e317473ae326094098fc71fa08e2e68dc05991c3889be80341573462adad9` → совпадает с `vars.ANDROID_CERT_FINGERPRINT` |
| Подпись | APK Signature Scheme v2, без v1 (minSdk 26) |

APK **не пересобирать и не переподписывать**: берётся ровно тот файл, который собрал
`.github/workflows/release.yml`. Проверка перед загрузкой (для `v0.2.2` — тот же
артефакт из релиза):

```bash
gh release download v0.2.2 --repo gazon1/sing --pattern 'singularity-0.2.2-android.apk'
sha256sum singularity-0.2.2-android.apk > sha256.txt
"$ANDROID_HOME/build-tools/37.0.0/aapt2" dump badging singularity-0.2.2-android.apk > badging.txt
"$ANDROID_HOME/build-tools/37.0.0/apksigner" verify --print-certs singularity-0.2.2-android.apk > certs.txt
```

Вывод пишется в файлы, а не в пайп: `cmd | head -1` убивает `cmd` по SIGPIPE, и
код возврата пайпа — это код возврата `head`, а не команды. Дальше эти файлы
(`sha256.txt`, `badging.txt`, `certs.txt`) сверяются с логом релиза и с
`vars.ANDROID_CERT_FINGERPRINT`.

## 3. Почему первую версию загружают руками

### Что отвечает API

Проверено 2026-11-17 (ключ из `~/.zshrc`, оба адреса):

```
GET /public/v1/application/com.singularity.todo/version  → 403
  {"code":"ERROR","message":"This user does not have rights to perform this action."}
GET /public/v1/application/2063789931/version             → 403 (тот же ответ)
```

Оба адреса — по `packageName` и по числовому `appId` — дают **одинаковый** ответ.
Это важно: по такому ответу нельзя отличить две разные причины.

### Что это значит

- `403 … does not have rights` — у ключа API нет в scope методов работы с версиями
  («создание версии», «загрузка APK», «отправка на модерацию») **или** нет доступа к
  этому приложению. Причина выбирается на стороне Console при генерации ключа:
  выбрать приложение `com.singularity.todo` и нужные методы (см. #3007).
- Отдельно, по справке RuStore, публикационный сценарий через API рассчитан на
  приложение, у которого уже есть активная версия, и начинается с создания черновика
  версии. У нас активной версии нет, поэтому bootstrap в любом случае делается в
  Console — и это снимает вопрос о правах ключа для первого шага.

Обе причины — «мало прав у ключа» и «нет активной версии» — ведут к одному решению:
**первую версию загружает человек в RuStore Console**. API используется для чтения
состояния и для последующих публикаций (#3000).

## 4. Авторизация в API

Хост: `https://public-api.rustore.ru`. (`public-api-m.rustore.ru` из этой сети
недоступен — TLS-ошибка.)

1. Подпись: `timestamp` = текущее время UTC в ISO-8601 с миллисекундами
   (`datetime.now(timezone.utc).isoformat(timespec="milliseconds")`), подпись =
   base64 от `SHA512withRSA(keyId + timestamp)`.
2. `POST /public/auth/` с телом `{"keyId","timestamp","signature"}` → `body.jwe`.
3. Токен живёт 900 секунд; каждый запрос — с заголовком `Public-Token: <jwe>`.

```bash
JWE=$(python3 - <<'PY'
import base64, datetime, json, os, subprocess, tempfile, urllib.request

base = "https://public-api.rustore.ru"
key_id = os.environ.get("RUSTORE_KEY_ID", "2351035476")
der = base64.b64decode(os.environ["RUSTORE_KEY"])

with tempfile.NamedTemporaryFile(suffix=".der") as key:
    key.write(der)
    key.flush()
    ts = datetime.datetime.now(datetime.timezone.utc).isoformat(timespec="milliseconds")
    sig = base64.b64encode(
        subprocess.run(
            ["openssl", "dgst", "-sha512", "-sign", key.name],
            input=(key_id + ts).encode(),
            capture_output=True,
            check=True,
        ).stdout
    ).decode()

body = json.dumps({"keyId": key_id, "timestamp": ts, "signature": sig}).encode()
req = urllib.request.Request(
    base + "/public/auth/",
    data=body,
    headers={"Content-Type": "application/json"},
)
with urllib.request.urlopen(req, timeout=30) as response:
    payload = json.loads(response.read())
raw = payload["body"]
print(json.loads(raw)["jwe"] if isinstance(raw, str) else raw["jwe"])
PY
)
curl -s -H "Public-Token: $JWE" https://public-api.rustore.ru/public/v1/application
```

`RUSTORE_KEY` — base64 приватного ключа (DER), `RUSTORE_KEY_ID` — его `keyId`
(см. п. 1: это идентификатор ключа, а не приложения). Приватный ключ на диск
пишется только на время подписи: `tempfile.NamedTemporaryFile` создаёт файл с
правами `600` и удаляет его при выходе из контекста, то есть сразу после того, как
`openssl` вернул подпись. Долгоживущего файла с ключом не остаётся.

Секрет (`RUSTORE_KEY`) **никогда** не попадает в репозиторий, логи или CI-лог. В
CI (#3001) — только GitHub Actions secrets. На машине, где API проверялся
2026-11-17, ключ лежал в `~/.zshrc`; на машине, где релиз собирается (2026-11-19),
такого файла нет и переменной в окружении тоже нет — то есть вызвать RuStore API
отсюда сейчас нельзя, ключ должен положить оператор.

## 5. Что делает человек в RuStore Console (bootstrap первой версии)

Порядок (по справке RuStore): черновик версии → APK → иконка и скриншоты →
заполнение карточки → отправка на модерацию → публикация.

1. **Имя приложения**: убрать ведущий пробел из `" sing"` (п. 1).
2. **Черновик версии**: версия `0.2.2`, versionCode `2002`. versionCode новой
   версии должен быть строго больше предыдущей (у `v0.2.1` — `2001`), поэтому
   берём релиз `v0.2.2`. Сама по себе `v0.2.1` не годится по другой причине —
   п. 8.
3. **APK**: артефакт джоба `release.yml` для тега `v0.2.2`
   (`singularity-0.2.2-android.apk`), подписан тем же ключом, что и остальные релизы;
   fingerprint сверяется с `vars.ANDROID_CERT_FINGERPRINT`. APK `v0.2.1` не грузить —
   из него пользователь не может выйти (п. 8).
4. **Иконка**: PNG 512×512 — `scripts/render_rustore_icon.py` (см. п. 6).
5. **Скриншоты**: от 1 до 10 (по справке RuStore), PNG/JPG, до 3 МБ каждый; кладём
   6 — по одному на каждый ключевой экран (см. п. 6).
6. **Карточка**: тексты из п. 7 — копируются как есть.
7. **Модерация**: отправка на модерацию; после одобрения — публикация.
   Публикация — действие человека, API её не делает за него.
8. **Зафиксировать**: после публикации — `appId` (уже известен: `2063789931`) и
   активный `versionCode` (`2002`) — их и ждёт #3001. Они уже записаны в п. 1;
   после публикации сверь их в Console и поправь п. 1, если RuStore присвоил
   другой `versionCode`.

## 6. Иконка и скриншоты

### Иконка 512×512

В репозитории максимум — растр 192×192 и два вектора адаптивной иконки
(`drawable/ic_launcher_background.xml`, `drawable-v24/ic_launcher_foreground.xml`).
Скрипт рендерит их в PNG 512×512 (видимая область адаптивной иконки — 72 из 108 dp):

```bash
pip install cairosvg pillow
python3 scripts/render_rustore_icon.py --out build/rustore/icon-512.png
```

Скрипт учитывает две особенности Android-формата, которые иначе тихо ломают
картинку: цвета в VectorDrawable — ARGB (`#AARRGGBB`), а SVG такого hex не знает,
поэтому альфа выносится в отдельный `*-opacity`; и штрихи (`strokeColor`,
`strokeWidth`) у вектора есть — без них сетка фона не рисуется. На это есть тест
`scripts/tests/test_render_rustore_icon.py`.

Два свойства результата, о которых стоит знать до загрузки:

- PNG получает альфа-маску со скруглёнными углами (радиус 64 при размере 512). Если
  RuStore требует непрозрачный фон, маску надо снять — но по справке прозрачные углы
  допустимы. Радиус задаётся флагом `--corner` и **не масштабируется** вместе с
  `--size`: при размере 1024 радиус останется 64.
- Рендер идёт из адаптивной иконки, поэтому логотип на нём крупнее, чем на
  legacy-растре `mipmap-xxxhdpi/ic_launcher.png`. Сверять надо с тем, что
  показывает устройство (адаптивная иконка), а не с legacy-картинкой.

### Скриншоты

Скриншоты показывают состояние с демонстрационными данными (реальные пользовательские
данные в публичных скриншотах недопустимы).

Сборки на скриншотах и в магазине — **разные**, и это осознанно:

- в магазин уходит **release-APK**, собранный `release.yml` (он же подписан ключом из
  GitHub secrets);
- скриншоты сняты с **debug-сборки**, потому что deep-link сидер `todo-debug://seed`
  существует только в debug-варианте (`androidApp/src/debug/AndroidManifest.xml`) и в
  release-APK его нет.

Интерфейс у обеих сборок одинаковый, отличается только номер версии и наличие сидера,
поэтому на скриншотах видно ровно то, что увидит пользователь магазина. Перед подачей
стоит убедиться, что release-APK запускается офлайн и открывается списком задач
(§8) — иначе скриншоты будут показывать то, чего у пользователя не будет.

Требования RuStore по справке: от 1 до 10 скриншотов мобильной версии, PNG/JPG,
до 3 МБ, не выше 2160×3840. Это **портрет 9:16**, а не ландшафт 16:9.

Рецепт (эмулятор, портрет 9:16, демо-данные):

```bash
# 1. Портрет 9:16 — так и просит RuStore.
adb shell wm size 1080x1920

# 2. Демо-данные: deep-link сидер из debug-сборки (todo-debug://seed?task=…&due=today).
#    Он живёт только в debug-варианте: в release APK его нет.

# 3. Снимок.
adb exec-out screencap -p > shot-01-agenda.png
```

Подходящие экраны: повестка дня, карточка задачи, заметки, календарь, список
предстоящего.

Съёмка набора скриншотов теперь одной командой: `SERIAL=capture_9x16 just sc`
(подробности — [`Maestro/README.md`](../../Maestro/README.md)). Она собирает
debug-сборку, ставит её на указанное устройство, прогоняет шесть capture-потоков в
порядке манифеста и проверяет каждый PNG: формат, целостность, размер 1080×1920
и пропорция 9:16. Сырые снимки лежат в `build/store-capture/`, рядом логи
Maestro. Ручной рецепт выше остаётся для отдельных экранов и для отладки.

Оговорка по языку: локализация в приложении частичная — ресурсные строки русские, а
нижнее меню и часть подписей («Good evening», «Today», «Add task», «No priority»)
захардкожены по-английски. Даты, кстати, всегда русские (`RussianDateFormatter`).
Поэтому скриншоты сняты в русской локоли, а английские подписи на них — реальный вид
приложения, а не ошибка съёмки.

## 7. Тексты карточки

Готовы к копипасте в Console. Ограничения RuStore: `shortDescription` ≤ 80 символов,
`fullDescription` ≤ 4000, `whatsNew` ≤ 5000, `moderInfo` ≤ 180, `privacyExplanation`
≤ 4000.

**Категория (до двух):** «Планирование и продуктивность» + «Заметки»
(точные названия выбираются из списка Console).

**Возрастная категория (`ageLegal`):** `0+`.

**Контакты разработчика:** e-mail `newbox2517@inbox.ru`; сайт не указывается.

**Политика конфиденциальности:** `docs/legal/PRIVACY.md` в этом репозитории; ссылка
для карточки — raw-файл GitHub:

```
https://raw.githubusercontent.com/gazon1/sing/main/docs/legal/PRIVACY.md
```

Ссылка работает только после мержа этой ветки в `main`: до этого файл лежит в ветке
PR, и raw-URL отдаёт 404. Либо вставьте текст политики в поле карточки из
`docs/legal/PRIVACY.md`, либо залейте ветку в `main` до подачи на модерацию.

**Краткое описание (`shortDescription`, ≤ 80):**

> Планировщик задач и заметок с ИИ, календарём и синхронизацией.

**Полное описание (`fullDescription`):**

> Singularity Todo — планировщик задач, который работает офлайн и остаётся вашим.
>
> Задачи с подзадачами, чек-листами, повторами, напоминаниями и зависимостями;
> проекты с цветом и иконкой; глобальные теги. Заметки с форматированием
> (жирный, курсив, код, списки) и экспортом в HTML.
>
> Agenda показывает день и неделю как расписание; календарь Google синхронизируется
> в обе стороны — события читаются и создаются из приложения.
>
> ИИ-ассистент умеет 44 вещи: переформулировать задачу, разбить её на шаги,
> сгруппировать похожие, придумать описание, собрать план недели. Провайдера и ключ
> вы выбираете сами (OpenAI, совместимый endpoint или локальный Ollama) — по умолчанию
> никуда ничего не отправляется.
>
> Синхронизация между устройствами — по вашему желанию, с разрешением конфликтов;
> резервные копии шифруются на устройстве перед выгрузкой. Приложение можно
> использовать без аккаунта: всё живёт в локальной базе.
>
> Плюс несколько профилей (личный, для ИИ-агента) и версия для десктопа.
>
> Рекламы, аналитики и трекеров нет.

**Что нового (`whatsNew`):**

> Первая публикация в RuStore.
>
> — Задачи, подзадачи, чек-листы, повторы, напоминания, зависимости
> — Проекты с цветом и иконкой, глобальные теги
> — Заметки с форматированием и экспортом в HTML
> — Agenda: день и неделя, двусторонняя синхронизация с календарём Google
> — ИИ-ассистент: 44 инструмента (переформулировать, разбить, сгруппировать, план недели)
> — Синхронизация между устройствами, зашифрованные резервные копии
> — Работа без аккаунта и без интернета

**Заметка для модератора (`moderInfo`, ≤ 180):**

> Офлайн-планировщик задач. Данные по умолчанию хранятся на устройстве; облако и
> ИИ включаются пользователем. Рекламы, аналитики и трекеров нет.

**Объяснение по приватности (`privacyExplanation`):**

> Приложение не содержит сервера разработчика: синхронизация идёт с тем Supabase,
> который вы подключаете сами (свой URL и публичный anon-ключ). Без сервера всё
> живёт в локальной базе. Бэкапы шифруются на устройстве (AES-GCM) и уходят в
> приватный бакет вашего сервера; вложения входят в бэкап, в синхронизацию — нет.
> ИИ-запросы уходят провайдеру, которого выбрали вы. Календарь Google — по вашему
> запросу. Системное резервное копирование Android может скопировать файлы и
> настройки в Google Drive. Аналитики и трекеров нет.
> Подробности: https://raw.githubusercontent.com/gazon1/sing/main/docs/legal/PRIVACY.md

**Данные для data-safety (`privacyDataTypes`):**

| Тип | Комментарий |
|---|---|
| `EMAIL` | адрес аккаунта (только если заведена учётная запись) |
| `USER_IDS` | идентификатор профиля; при синхронизации — идентификатор узла часов (HLC), производный от идентификатора устройства |

## 8. Известные ограничения текущего релиза

- **APK `v0.2.1` в RuStore публиковать нельзя: из него не выйти.** Он собран без
  `supabase.url` / `supabase.anonKey` (release.yml инжектит только `google.client.id`),
  поэтому первый запуск у пользователя магазина показывает экран «Connect your server».
  В сборке `v0.2.1` на этом экране кнопки выхода нет — она там появилась позже
  (`LoginScreen.kt`, `AUTH_CONTINUE_OFFLINE_BUTTON`), и экран для пользователя магазина
  становится тупиком.

  Проверено на устройстве: `v0.2.1` → экран «Connect your server» с двумя полями и
  кнопкой «Save», выхода нет; сборка из `main` → сразу открывается список задач.

  Значит в магазин идёт релиз из `main`, где офлайн-старт есть. Нужен новый тег
  (`v0.2.2` → versionCode `2002`): у `v0.2.1` versionCode `2001`, а RuStore требует,
  чтобы versionCode новой версии был строго больше предыдущей. Но причина, по
  которой `v0.2.1` не годится, — именно дефект офлайн-выхода, а не versionCode:
  выше `2001` не поднять, а вот починить офлайн-выход — можно.
- **Имя приложения в Console — `" sing"`, с ведущим пробелом.** Поправить до подачи
  на модерацию (п. 1, п. 5).
- Скриншоты для карточки сняты с debug-сборки из `main` — с демо-данными и офлайн-режимом.
  Это ровно то, что увидит пользователь магазина, кроме номера версии в сборке; в
  магазин при этом уходит release-APK (§6).
- Локализация частичная: подписи нижнего меню и части экранов захардкожены
  по-английски, даты — всегда по-русски. Это видно на скриншотах и это реальный вид
  приложения.
- Хостинговый Supabase-проект сейчас в статусе `INACTIVE`. Даже если он поднимется,
  зашивать его URL и anon key в релиз — отдельное решение: это публичный идентификатор
  проекта, и синхронизация всех пользователей магазина пойдёт через него. По умолчанию
  приложение работает офлайн, а сервер пользователь подключает сам.
- Ссылка обновления `https://rustore.ru/app/com.singularity.todo` взята из кода
  приложения (`RuStoreUpdateStore.kt`). Сверьте её с фактическим адресом карточки
  после публикации: если Console выдаст другой slug, поправить надо и код, и
  `RemoteConfigSnapshot` (#3001).
