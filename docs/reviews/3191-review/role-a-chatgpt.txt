In particular, I checked the following.

### 1. Navigation state restoration

**Pass.**

- `rememberSaveable` replaces the non-persistent `remember` for the selected top-level route.
- The saver uses the same polymorphic `NavKey` registration as the navigation back stacks.
- Restored routes are checked against `allowedRoutes`.

The two new tests cover successful restoration and rejection of a non-top-level route.

One limitation: the tests exercise the codec and state invariant, not an actual Android Activity recreation or process-death restoration. The existing Maestro rotation flow supplies the important device-level evidence.

### 2. Undo notification

**Pass.**

`NotificationHost.kt` changes only the `Notification.Undo` branch to `SnackbarDuration.Long`.

The ordinary Toast branch remains `Short`.

The guard test checks both behaviours. The implementation also preserves the existing distinction between accepting and declining the undo action.

### 3. Maestro flows and helpers

**Pass.**

I checked the changed flows against the surrounding helper conventions.

Notable observations:

- The pinned-filter flow waits for the asynchronous pin operation.
- The empty-search flow dismisses the keyboard before looking for the recovery control.
- The rename flow checks the actual reverted title, not merely the existence of the input.
- The full-task creation flow dismisses the keyboard before looking for fields below the fold.
- The reminder flow now supplies the required due date.
- The logbook flow scrolls to the note before asserting its visibility.
- The delete/undo flow leaves through the editor's top-bar control rather than sending Back to the popup window.

**Attachment helper question: removing `centerElement` is not a finding.**

The change is justified.

The `+ Add file` row is the last element in the sheet. Centering it can keep scrolling towards an unreachable position until the timeout expires. The replacement uses ordinary `scrollUntilVisible` and taps at `50%,25%` within the row.

That preserves a useful tap location without requiring the row to be centered. The qualification evidence also covers the affected attachment flows.

I found no reason to restore centering.

### 4. Orientation fixture

**Pass, with a documented limitation.**

The implementation:

- Reads the original rotation settings once per device.
- Preserves individually readable settings.
- Restores them once at the end of the run.
- Checks device availability before restoration.
- Registers restoration after the screen-off callback, so reverse callback execution restores orientation while the screen is awake.

The ten fixture tests cover the important restoration cases.

One consciously accepted limitation deserves attention: a setting that cannot be read cannot be restored. The implementation warns about this rather than pretending restoration succeeded. This is a documented best-effort contract, not an undisclosed regression.

## Implicit-decisions audit

These are consequential choices I identified beyond the narrowly stated acceptance requirements. They are intentional decisions, not findings.

| Decision | Alternatives | Evidence and rationale | Behavioural guarantee |
|---|---|---|---|
| Save only the selected top-level route | Save the previous-tab history too | Existing private state and narrower navigation API; documented in the ADR | Back at the root of a tab returns to Today after rotation |
| Fall back to Today when a saved route cannot be decoded | Fail restoration or attempt a migration | Avoids crashing on obsolete saved state | Restoration is not guaranteed for incompatible payloads |
| Apply the longer snackbar duration to all Undo notifications | Special-case task deletion | Shared notification semantics and Material 3 guidance | Every Undo offer gets ten seconds |
| Restore orientation only for readable settings | Refuse to run if either setting cannot be read | Best-effort device fixture with explicit warnings | An unreadable original setting cannot be guaranteed to survive unchanged |
| Use a fixed point inside the attachment row | Center the row before tapping | Measured scrolling timeout and gesture-navigation geometry | The tap no longer depends on centered positioning |
| Leave through the top bar after accepting Undo | Send Back and attempt to reach the underlying editor | Popup-window focus behaviour observed during qualification | Navigation explicitly targets the editor rather than the popup |

The first decision deserves particular emphasis: this PR restores the selected tab, not the entire navigation history. The ADR makes that limitation explicit. I consider the scope defensible because the previous implementation already lost that history on Activity recreation.
