# R8 full mode removed two things the release APK needs at runtime

## Context

The release APK of run `39966227235` (`0.0.4`) died on launch, before `MainActivity`
ever ran. On a physical device (Android 15, API 35) the process was killed during
provider installation:

```
FATAL EXCEPTION: main
java.lang.RuntimeException: Unable to get provider androidx.startup.InitializationProvider
Caused by: java.lang.NoSuchMethodException: androidx.work.impl.WorkDatabase_Impl.<init> []
        at androidx.work.WorkManagerInitializer.b(...)
        at androidx.startup.InitializationProvider.onCreate(...)
```

The debug APK built from the same commit works, so the defect belongs to the
shrinking step and not to the code. The `usage.txt` and `configuration.txt` of a
local release build of the same commit say exactly what R8 removed:

```
androidx.work.impl.WorkDatabase_Impl:
    public void <init>()              <-- removed
    public void clearAllTables()      <-- removed
    ...

com.singularity.todo.BuildConfig:
    public static final java.lang.String SUPABASE_URL    <-- removed
    public static final java.lang.String VERSION_NAME   <-- removed
    ... (every field and the constructor)
```

`mapping.txt` shows `com.singularity.todo.BuildConfig -> hy0:` — the class survived
under a new name, with nothing in it.

Two independent mechanisms are behind this, and both come from R8 **full mode** —
what AGP 9 uses by default, and what it turns on through
`android.r8.strictFullModeForKeepRules`. The documented difference from
compatibility mode is that
"the default constructor (`<init>()`) is not implicitly kept when a class is kept"
and that "classes that are only instantiated using reflection should be kept
explicitly with a `-keep` rule".

**1. The WorkManager database.** WorkManager 2.10.0 brings `androidx.room:room-runtime:2.6.1`,
which has its own database `androidx.work.impl.WorkDatabase`. Room 2.6.1 creates the
generated implementation reflectively:

```
Room.getGeneratedImplementation()
    -> Class.forName("androidx.work.impl.WorkDatabase_Impl")
    -> Class.getDeclaredConstructor()      // empty Class[] — a no-arg constructor
```

Room 2.6.1's consumer rule is `-keep class * extends androidx.room.RoomDatabase` — the
class is kept, but with no member specification, so the constructor is not. Room 3
(`androidx.room3`), which this repository uses for its own database, ships
`-keep class * extends androidx.room3.RoomDatabase { void <init>(); }` — the explicit
constructor. Room 3 fixed this for itself; Room 2.6.1 did not, and the repository has
both on the classpath at once.

**2. `BuildConfig`.** `shared` compiles before `androidApp` generates `BuildConfig`,
so it reads the build-time values through reflection:

```kotlin
Class.forName("com.singularity.todo.BuildConfig").getField("SUPABASE_URL")
```

R8 resolves a constant-string `Class.forName` to a class reference and then treats the
class like any other: it renamed it and removed every field, because nothing in the
program reads them statically. The reflective lookup found a class with no
`SUPABASE_URL` field.

## Idea

Two options were available.

*Keep the release build out of R8's reach* — `isMinifyEnabled = false`. It would have
fixed both defects, and it is the option that has no new rules to maintain. It was
rejected: the release APK would grow by roughly the size of the whole dependency
graph, and the two rules below cost four lines.

*Keep what reflection needs.* Explicit `-keep` rules for the members that are only
ever reached reflectively. This is the option the R8 documentation prescribes, and it
keeps the shrinker doing its job everywhere else.

## Decision

The release build keeps two things explicitly, in `androidApp/proguard-rules.pro`:

```proguard
-keep class * extends androidx.room.RoomDatabase { <init>(...); }
-keep class com.singularity.todo.BuildConfig { *; }
```

The first rule is deliberately about Room **2**: it covers every Room 2 database that
arrives through a dependency, not just WorkManager's, and it does not duplicate Room
3's own rule, which already keeps its constructor.

The second rule keeps the class *and* its fields: the class because `Class.forName`
resolves it by name, the fields because `getField` resolves them by name.

The reflective readers stay reflective. The alternative — moving the build-time values
out of `shared` — is a larger change to the module graph than the defect warrants,
and the reflection is a consequence of a real constraint (a KMP module cannot import a
class generated by a later one).

## Rationale

The defect was invisible to every gate in the repository because none of them ever
built a minified APK: the free leg of `ci.yml` compiles only, the pro leg assembles
`assembleDebug`, and `release.yml` builds `assembleRelease` and publishes it without
ever installing it. Debug and release are different programs, and the difference is
exactly where both of these defects lived.

The rules are placed next to each other with the evidence in the comments, because the
next person to see "R8 removed my constructor" should not have to re-derive it from
`usage.txt`.

## Consequences

- A dependency that ships a Room 2 database is covered by the existing rule. A
  dependency that reads its own configuration reflectively is not — it will need its
  own rule, and the failure will look like a `NoSuchFieldException` on a field that
  plainly exists in the source.
- R8 matches a keep rule against the input hierarchy, not against what survives the
  merge: in the fixed build `androidx.room.RoomDatabase` was merged away entirely and
  `WorkDatabase` extends `java.lang.Object`. The rule works anyway, but "the class is
  kept" is not a promise about the base class it had.
- `buildTimeGoogleClientId()` was already wrapped in `runCatching`; the other two
  readers (`buildTimeSupabaseConfig()`, `appVersion()`) are not. A missing field is
  still an uncaught exception there. Making them fail-safe is a separate change, and
  the keep rule is what makes them correct.
- The release APK must be launched on a device before it ships. Until that gate
  exists, every future keep rule is a guess about what else the shrinker removed —
  `usage.txt` is the only honest inventory of that.
