## Context

After the ULID→UUID migration (#238) the question arose: should the app use
UUID v4 (random) or UUID v7 (time-ordered)?  `Uuid.random()` in `IdGen.kt`
generates v4; `Uuid.generateV7()` is also available in Kotlin 2.4 stdlib.

UUIDv7 advantages:
- Lexically time-ordered: 199/200 IDs increase lexically vs 98/200 for v4.
  Physically close IDs → B-tree insert locality → better DB page utilization.
- Natural insert-time ordering without a separate `createdAt` sort index.

UUIDv7 risks:
- Clock monotonicity: if the system clock jumps backward, v7 can produce
  IDs that are older than existing ones. HLC mitigates this (see below),
  but the on-device clock is still the entropy source.
- Inference risk: in multi-user sync, a client could enumerate nearby v7
  IDs to guess other users' entities. For a personal app this is not a
  threat model, but it is a real concern for collaborative products.
- Throughput ceiling: 2^48 IDs per millisecond per node. A very large
  personal instance would never approach this, but the constraint is
  real for server-side generation.

## Decision

**Keep UUID v4 (`Uuid.random()`).**

Causal ordering between devices is already guaranteed by Hybrid Logical
Clocks (HLC) in the sync layer (`Hlc.generate()`).  An entity's position
in a total order is determined by `(hlc, localUuid)` — the ID itself
carries no semantic meaning beyond uniqueness.

The HLC layer is the **authoritative** ordering mechanism; an ID that
happens to be lexically sortable is a coincidence, not a contract.
Relying on v7's time-ordering for causal ordering would also require
 auditing every place that reads IDs to confirm they assume order,
 creating coupling between ID format and query logic.

The DB schema uses no `ORDER BY id` anywhere (verified 2026-10-08, zero
matches across all SQL files).  Every mutable query is either a point
lookup by primary key or a full-table scan with a business-key sort
(`sort_order`, `hlc`).  The B-tree insert locality argument for v7
therefore has **zero practical effect** on this codebase.

## Consequences

- `nextId()` stays as `Uuid.random().toString()` — no code change.
- `IdGenerator` interface and all implementations remain unchanged.
- The `PROVENANCE.md` entry for `kotlin-stdlib` already covers UUIDs;
  no new license entries required.
- If a future collaborative feature requires server-side ID generation,
  that decision belongs in the sync ADR (`2026-10-04-sync-server-schema-and-merge`)
  and not here.
- Documentation that previously asserted "no ordering guarantee" (e.g.
  `2026-10-06-recurrence-roll-forward-is-already-idempotent.md` lines 75-76)
  is **correct** as written for v4, and must be updated if v7 is ever
  adopted.
