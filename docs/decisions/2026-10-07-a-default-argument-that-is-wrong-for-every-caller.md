# A default argument that is wrong for every caller who does not notice it

`SettingsSwitchRow` — the shared "labelled row with a switch" widget — declared its automation
tag as `testTag: String = TestTags.Settings.DARK_THEME_SWITCH`. Measured over the tree: **15 of
its 16 call sites omitted the parameter.** The remaining one is the real dark-theme switch.

So every toggle in the app carried the dark-theme switch's tag: notifications on/off, sound,
vibration, Saturday, Sunday, "has description", "pinned", calendar-sync enable, calendar-sync
import-from-Google.

## Why this is not a naming nit

`onNodeWithTag` throws on more than one match. Any test that found `DARK_THEME_SWITCH` was
implicitly relying on the other fifteen being absent, which is true on `InterfaceSettingsScreen`
and false everywhere else:

- a screen rendering **two** untagged switches was not untestable — it was *broken for tests*,
  because the selector matched twice and threw;
- a test targeting the dark-theme switch from a screen that also renders another switch would
  fail with "expected 1 node, found 2" and no obvious cause.

Nothing caught it, because the tag was never wrong from the compiler's point of view and the
one test that exercises that row happens to sit on the screen where the default happens to be
correct.

## Why a default is the wrong shape here

The parameter documents itself as *"the tag this row carries"*, and a default silently answers
the question for every caller who does not ask. That is the same defect as ADR
`2026-10-07-three-files-that-only-one-gate-reads` seen from the signature side: a single-consumer
contract with no producer check. The difference is severity — a golden file fails loudly when the
gate runs, whereas this compiled, ran, and was wrong.

**`testTag` is now required with no default.** 16 call sites name their own tag, and a 17th
cannot be added without one. A parameter with no default cannot lie about the caller.

## Decision

Removed the default. All 16 call sites pass an explicit tag, named per control
(`TestTags.Settings.NOTIFICATIONS_SOUND_SWITCH`, `TestTags.SearchFilter.PINNED_SWITCH`,
`TestTags.CalendarSync.GOOGLE_IMPORT_SWITCH`, …). New constants rather than reusing
`DARK_THEME_SWITCH` for convenience — the whole point is that the tag names *which* control it is.

`GoogleCredentials.canRenew` is left as a derived property over `refreshToken` rather than
taking a boolean, for the same reason: a caller passing `canRenew = false` could disagree with
the credential it constructed, and the screen's renewal warning renders exactly that property.

## The other half: a screen with no tags at all

`CalendarSyncSettingsScreen` had **zero** `testTags` across 592 lines. Not untagged controls —
the entire panel. So no automation could reach any of its user-visible behaviour however well
the ViewModel was tested, which is why the feature reached 23 passing unit-test classes, 8
OpenSpec requirements, and **0 scenario carriers** while looking thoroughly covered.

That is the generalisable half of this ADR: *a screen can be complete and still have no
address*. Reachability is a precondition for measurement, not a consequence of it.

## Consequences

- The same trap exists for any Compose widget that takes an optional tag. The ones in
  `core/ui/components` were audited; `SettingsSwitchRow` was the only one with a misleading
  default. Others take `modifier` and are used correctly.
- **A second, unsolved instance of the same class, recorded rather than fixed here.**
  `TestTags.settingsTab(name: String)` is called with the enum *name* — `settingsTab("Calendar")`,
  not `settingsTab("calendar")` — because `SettingsScreen` tags with `TestTags.settingsTab(tab.name)`.
  `SettingsTab` is `private`, so a test cannot reference it and the rule exists only as
  `slug()` lowercasing its input. A test that got the case wrong failed on
  `AssertionError: Tag 'settings_tab_calendar' is not in the semantics tree` — a correct,
  loud failure, so it is much less dangerous than the default-argument case, but it is
  still a fact enforced nowhere. The fix would be to make the tab names a public
  `List<String>` (or the enum itself `internal`) so a carrier cannot spell them wrongly;
  that is a production-API change and was not made while verifying the tags themselves.
- `Maestro/TAGS.md` is regenerated by `TestTagsCatalogJvmTest` and must be refreshed with
  `-PupdateGoldens=true`, then re-run clean — the new constants are not usable until it is.
- Scenario carriers only count in `desktopApp/src/jvmTest` and `androidApp/src/androidTest`
  (`_kt_root_to_target` in `infra/kiwi/traceability/links.py`), so `shared/commonTest` cannot
  carry one. The 23 calendar-sync unit tests therefore could not have become carriers even
  once tags existed.

## Addendum (same day): a second instance, found by the *symptom* nobody could read

Writing the first carrier for `CAL-SYNC-PROVIDER-01` meant opening Settings from a
desktop flow test — something **no desktop flow test had ever done**. It hung: 30 minutes
at 99% CPU inside `RenderNode_nDrawInto`, no exception, no failure message.

The bundle said it plainly once read:

```
+0.78s  awaitContentDescription(Settings)    OK
+1.92s  awaitContentDescription(Settings)    FAIL  InstanceCreationException:
       Could not create instance for '[Factory: '…SettingsViewModel']'
```

`testPlatformModule()` **replaces** `platformModule()` in the harness, so every definition
in the platform module must be re-declared in the test module — and two were not:
`LogBundleExporter` and `FileSharePort`. Both are constructor parameters of
`SettingsViewModel`, so the whole Settings screen was unconstructable in any test, and
Compose's retry-every-frame on a composition failure turned that into an infinite redraw
rather than a catchable error.

**Then the parity test found six more.** `TestPlatformModuleParityTest` already existed,
with a docstring that described this exact symptom, and it compared only names ending in
`Dao`. Widening it to every port type immediately named the rest:

```
[HostEnvironmentPort, BackgroundWorkScheduler, CoroutineScope, Notifier, GoogleSyncPeriodicTrigger]
```

Seven latent landmines in total, none of which had ever fired — because no test had
reached the code resolving them. Each one *would* have cost the same 30-minute,
no-message hang.

Two decisions follow, and both are about the check rather than the bindings:

- **The DAO filter was the bug, not the DAO bindings.** It was written after the DAO half of
  this defect shipped and generalised no further, so it protected exactly the case it had
  already seen. A check named for what it compares will be re-run against a second case and
  found wanting; the replacement compares `platformModule()` against `testPlatformModule()`
  for *every* type.
- **`String` is the one legitimate exclusion**, and the exclusion is documented at the
  filter: production binds a backups directory *and* a logs directory, the test module binds
  a temp backups path and passes the logs path to the `LogBundleExporter` constructor
  directly. A parity check that reports a difference which is not one gets deleted, and a
  deleted check protects nothing.

The new bindings are inert where the production form would start a thread
(`BackgroundWorkScheduler`, `GoogleSyncPeriodicTrigger`) or a `notify-send` (`Notifier`),
real where the production form is pure (`JvmHostEnvironment`), and the `CoroutineScope` is
**already cancelled** — a live one would hand a real `Dispatchers.Default` scope to whatever
resolved it, and a job launched there outlives its test class.

### The lesson worth more than the seven bindings

Two of the three carriers that first failed did so with a message naming the wrong layer —
"sync button not displayed" for a binding three layers down, "no failure text" for a
coordinator never replaced. **The composition retry loop converts every DI failure into an
infinite redraw**, so the observable is always "a thing is missing", never "a thing threw".

That is why this file is an ADR and not a backlog entry: the seven bindings are a chore,
but "a missing Koin definition is indistinguishable from a missing UI element" is a
property of the harness that will produce the next expensive diagnosis too.
