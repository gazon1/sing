## Context

`render-adr-tools-section.py` reads `AdrSurface.kt` and `McpToolCatalog.kt` to generate
the "ADR tools" block in two skill documents. The alternative — executing a built CLI —
was deliberately not chosen.

## Decision

The renderer **parses** the Kotlin source files rather than executing any compiled artifact.

## Rationale

`scripts/ci/static-gates.sh` is specified to complete without a JVM. Adding a step that
shells out to a Gradle-built CLI would make the cheapest gate in the repository the
slowest. The gate must be fast enough to run on every push without Gradle; executing a
CLI would violate that constraint.

The cost of parsing is fragility: a declaration the renderer cannot read must be an
error, not a silent omission. This was tested and manifested twice before the rules
were tightened:

1. `write_adr` description was rendered as `list_adrs`'s description. The Kotlin
   declaration uses string concatenation across lines, which pushed the `annotations`
   field onto a later line. The regex matched across the boundary and captured the
   next entry's description. The renderer now splits on `ToolEntry(` chunks and reads
   each one independently, preventing cross-entry bleed.
2. A multi-line `AdrCommandSpec` declaration broke the renderer entirely. The
   `AdrCommandSpec` / `AdrFlagSpec` calls are now required to be one declaration per
   line; the parser raises `ParseError` on anything else.

## Consequences

- The renderer requires a specific source format. Reformatting a declaration across
  lines will produce a `ParseError` with a diagnostic message, not silent omission.
  This is the intended behavior — the skill must not look complete while missing a
  command.
- The gate (`check-skill-drift.py`) fires on any divergence between the rendered
  block and the current tool surface. Running the renderer regenerates the skills;
  the gate confirms the committed text matches.
- If the Kotlin source shape changes substantially, the renderer must be updated.
  This is caught by the gate, not by a test that exercises only the happy path.

## Alternatives Considered

**Execute the built CLI** (`singularity-adr --help`). Rejected: requires Gradle,
adds seconds to a gate that must run in CI without a JVM. The rendering step is
already in the skills pipeline and need not be gated.

**Generate a machine-readable manifest from Kotlin at build time** (e.g., a Gradle
task that emits `adr-tools-manifest.json`). Would move the check back into the JVM
while keeping the gate fast (manifest = data, not code). Not implemented; the
current approach works and the fragility has been addressed with the chunk-based
parser and the one-declaration-per-line rule.
