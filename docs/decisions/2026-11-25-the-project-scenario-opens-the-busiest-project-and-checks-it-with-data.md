# Сценарий проекта открывает самый насыщенный проект и проверяется данными

## Context

Desktop-сценарий открытия проекта выбирал **первую видимую карточку** в списке
проектов. Это недетерминированно по смыслу: базовая линия — описание поведения
приложения, а «первая видимая карточка» зависит от порядка сортировки и от того,
что влезает в окно. Android-сценарий при этом выбирал проект с наибольшим числом
задач (в текущем датасете — «Project 39»).

Вторая половина проблемы — проверка. Экран детали проекта считался открытым
по наличию одного тега (`PROJECT_DETAIL_QUICK_ADD`). Это доказывает, что поле
быстрое добавление нарисовано, но не доказывает, что на экране **тот самый**
проект: тигл присутствует на любой карточке проекта.

## Idea

- Оба платформы открывают один и тот же проект: самый насыщенный датасета.
- Идентичность экрана доказывается **содержимым**, а не присутствием виджета.

## Decision

**Выбор проекта — по данным, а не по порядку на экране.**

Датасет знает число задач каждого проекта (`frameTimeProjectCounts`), поэтому
тест выбирает проект с наибольшим счётчиком (`projectWithMostTasks()`; при равенстве
— по имени, чтобы выбор был воспроизводим). Проект открывается через поиск
(`TestTags.PROJECTS_SEARCH_INPUT`, `typeIntoTag` — замена текста), чтобы не
зависеть от прокрутки и сортировки списка. Поиск — часть подготовки, он не
таймируется; таймируется открытие карточки.

**Проверка экрана опирается на данные.**

`verifyFrameTimeProject(subject)` требует:

- числа задач проекта больше превью-лимита (`PROJECT_PREVIEW_LIMIT = 5`), иначе
  экран не отличить от пустого состояния;
- непустого набора строк превью, каждая из которых помечена тегом этого
  проекта (`projectTaskTags`) — то есть на экране нет чужих строк;
- текста «See all N tasks», где N совпадает с полным счётчиком задач проекта
  в датасете, — это подтверждает, что открыт нужный проект, а не другой.

Наличие `PROJECT_DETAIL_QUICK_ADD` остаётся как условие «экран открыт», но
идентичность проверяется содержимым.

**Связанные задачи проверяются по строкам.**

`verifyFrameTimeRelations` больше не ограничивается тем, что секция related
tasks вообще нарисована: секция раскрывается (клик по
`TASK_DETAIL_RELATED_TASKS_SECTION`) и для каждой зависимости проверяется
конкретная строка `TestTags.relatedTaskItem(id)`. Экран детали задачи — не
`LazyColumn`, а `verticalScroll`, поэтому содержимое скомпоновано целиком и
строки ищутся без прокрутки.

## Rationale

- Базовая линия должна быть воспроизводима: тот же датасет — тот же проект.
  «Первая видимая карточка» воспроизводима только при том же порядке и том же
  окне.
- Android и desktop должны мерять одно и то же состояние, иначе сравнение
  платформ бессмысленно.
- Тег на экране — слабое доказательство: он не различает два разных проекта.
  Данные различают: строки превью принадлежат конкретному проекту, а «See all
  108 tasks» называет его полный счётчик.
- Проверка «нет чужих строк» на экране детали намеренно не делается: рядом
  может оказаться соседняя панель со своими строками, и такая проверка была бы
  хрупкой. Принадлежность строк проекту проверяется по тегам строк.

## Consequences

- Набор desktop-сценариев теперь явно закреплён за «Project 39» (108 задач) в
  текущем датасете; при смене датасета проект выбирается заново автоматически.
- Сценарий длиннее: подготовка включает ввод в поиск. Время ввода не входит в
  измеряемую величину, но сценарий в целом занимает больше времени.
- Проверка related tasks стала строже: если секция не раскрывается или
  зависимость не нарисована, замер падает, а не проходит с «нулевой»
  проверкой.
