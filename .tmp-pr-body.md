## What this is

The follow-up batch after #756: eleven changes that close the open findings and
make the tools that were supposed to catch them actually catch them.

Six of them (A1–A6) are about the measurement layer, five (B1–B5) about the
code the measurements were pointing at.

### A1 — the nightly flake-rate measurement, which never measured anything

The nightly has failed on every night it has run: six runs, six identical
issues titled "found an unacknowledged flake". No flake was ever found.

Two causes, both in the workflow. `flake.yml` never installed the gate
tooling, and the measuring script imports the gate package, which imports
`loguru` — so the script died before it measured anything. And the issue
step's condition was `failure()`, which cannot tell "the rate exceeded the
ceiling" from "the measurement could not be completed": the first is a
finding about a test, the second is a finding about the measurement, and
the issue it opened claimed the first.

The measuring script now writes a **verdict** — `clean`, `found`, `broken` —
on every path out, including the ones where it exits 1. The workflow reads
the verdict rather than the exit status and opens two different issues: one
for a flake it found, whose body names the test ids, and one for a
measurement that did not run, which says why.

The six false issues are closed with a comment saying what they were.

### A2 — "nothing ran" and "ran below the floor" are different verdicts

`check-test-runs.py` answers two questions with two exit codes: 3 means
there was no report at all, so no floor was compared; 1 means a report
exists and is below the floor, so the suite ran and lost coverage. They
send the reader to different places.

The CI step ran three invocations in a row and stopped at the first
non-zero code, so a missing report for one target hid the other two
verdicts. All three are now executed, all three verdicts are printed, and
the step distinguishes the two failures in its message. `check.sh` had the
same conflation, with one message for both.

### A3 — the device tier says what it did, where the reader is looking

The instrumented run now writes a verdict into the job summary: the tier,
the counts, the names of the failing tests, and one of four verdicts —
**passed**, **failed**, **did not run**, **could not read**. The distinction
between "failed" and "did not run" is the point: a red X that means
"nothing happened" reads like "the app is broken".

The summary never fails the job it summarises.

### A4 — a red shard can be reproduced locally

The nightly's shard count lived in the workflow's `plan` job as two
literals, and a local run had to guess it. A wrong guess does not fail — it
runs *different flows*, because the shard is `index % shards` over the
sorted list. A reproduction that guessed wrong comes back green and says
nothing about the shard that failed.

The count moves into `config/docs/e2e-shards.txt`, which the nightly's plan
job reads to build its matrix. `scripts/e2e-shard-plan.py` reads the same
file and prints the flows a shard holds and the commands that reproduce it.
The plan script asks the runner for its flow list and suite selection
rather than re-implementing them, so the two cannot drift.

### A5 — an archived change lives in the live spec

Six changes had every task checked and their requirements already shipped,
and they sat in `openspec/changes/` because archiving is a step nobody was
doing. A directory where finished work and pending work look identical is a
directory nobody can read.

They are archived, and their requirements are merged into the live specs:
REQ-19..REQ-22 and the modified REQ-18 into `test-execution-integrity`, the
offline session's requirements into `user-authentication`, the two
working-day requirements into `tasks`, and `write-pipeline` — thirteen
requirements, forty citations, no spec — becomes a live spec of its own.

The live `test-execution-integrity` spec also had two requirements called
REQ-13. The per-scenario rule keeps the number (an ADR names it) and the
by-results check takes REQ-23.

### A6 — two advisory gates become blocking

`unwired surfaces` could not see an injection it did not spell out.
`single<AuthRepository> { SupabaseAuthRepository(gateway = get()) }` gives
AuthGateway to the repository, but Koin's `get()` takes its type from the
parameter it fills — so a scan that only recognised `get<Name>()` called
every such binding an orphan. All three of the gate's findings were false,
and all three were false for that reason: the most common injection shape
in the codebase.

The fix had been an allowlist: thirty-odd names, each a claim somebody
audited by hand. So the detector resolves the missing fact instead — it
indexes every class's constructor parameters and reads the type behind a
bare `get()` off the parameter it fills, by name or by position. A
constructor reference (`viewModelOf(::MyVm)`) is the same fact written
differently. The floor goes to zero, the gate becomes blocking, and it
gets a control that plants a binding nothing injects.

`script conventions` was advisory for a second reason: it detected
`argparse` by looking for the substring `"import argparse"`, which matches
its own detection needle — so the checker reported *itself* as a violation
and the corpus was never green. It parses the module now. With the last
three argparse holdouts migrated, the gate goes blocking too, with a
control that adds the import back.

### B1 — the bounded read is a shared primitive

The remote-config port had a private method for "read this, but not longer
than the port's deadline": a scope of its own, a timeout around the wait,
and a report of a failure that arrived after the caller gave up. That shape
is not private — a deadline in a caller can only end a *cooperative* read,
and a read that blocks inside a driver call ignores cancellation entirely.

The primitive says *that* the deadline was missed and never *what to do
about it*. The port's behaviour is unchanged.

### B2 — the shell question is answered on the JVM tier

The device smoke asks three questions, and the third — do the shell's test
tags reach the accessibility tree — has a portable half. "Does a Compose
`testTag` reach the semantics tree at all?" is a question about the shared
UI, and the shared UI runs on the JVM tier in seconds.

So the question splits: the JVM tier asserts the tag reaches the semantics
tree, the device tier keeps the part that is Android's (`resource-id`).
`docs/testing/what-each-tier-proves.md` states the split.

### B3 — a flow asserts on structure, not on the app's copy

The flows asserted on strings: "October 2026", "Month", "Today", "OK".
Every one is a string the app may translate, and the emulator in CI runs
with a Russian locale. A flow that asserts on the app's copy passes on the
developer's machine in English and fails in CI in Russian, and the failure
reads as "the app is broken".

The flows now address elements: a day cell by a tag that carries the date,
the mode control by its test tag, the date picker's cells by the day number
as a standalone number.

The auth flows had the same shape of problem in the state rather than in
the text: they expected a signed-in app and met one, because a previous
flow had signed in. They cleared the device to fix it. The app is now
signed out for the auth flows, through the debug deep link that calls
`AuthRepository.signOut()` — the same call the app's own button makes — and
the runner performs that reset before every flow.

The locale was **not** the cause of the calendar failures: the month title
comes from `Month.displayName()`, which returns the English enum name.
Those flows were cascade victims of the cleanup that never matched, and
they are green for that reason now.

### B4 — a search that matched nothing is an answer, not a blank screen

The search screen was supposed to show three states, and it showed two of
them wrongly. Three Maestro flows say so in their comments. The app
contradicted them: a query that matched nothing returned a list of tasks —
the nightly screenshot shows three "Buy milk" tasks and other flows' seeds
— so the no-results state never appeared and the flow could only pass by
accident.

The cause was not in the screen; it was one layer down, in the query
resolver. A word that matches no condition rule is a `HasText` condition,
and the resolver put it into `freeText` and produced no predicate for
tasks at all — so every task came back for every query.

The resolver now filters tasks by the text, reusing the tasks feature's own
rule, and the three-state decision moves into a pure function the
composable calls.

## Not in this change

- The `req id uniqueness` gate is still not in the static tier. The corpus
  is green for the requirement ids now, so it can move next.
- `auth/08`, `auth/09` and the backup flow still use `clearState: true` —
  the real-server and backup paths.
- Notes, projects and tags still match the joined `freeText` phrase, so a
  multi-word query treats tasks and notes differently. That was already
  true; changing it would change existing result behaviour.
