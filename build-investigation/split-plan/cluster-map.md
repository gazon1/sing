# Phase 1 — hot clusters, and what blocks a split

Window: commits since 2026-05-05 (1,428 commits touching `shared/src`), tree at `2b4cf8318`.
Generated by `analyse.py --since 2026-05-05`; every number below is copied from `cluster-data.tsv`,
`hot-files.txt`, `hot-packages.txt`, `co-changes.txt` or `package-graph.txt` in this directory.

Production = `commonMain` + `jvmMain` + `androidMain`, 1,298 files. Test source sets (669 files) are
counted apart: a hot test file says where the tests are, not where a module boundary belongs.

## What the numbers say

1. **`:shared` is one strongly connected component.** 183 of 243 packages, and 52 of 81 clusters,
   can all reach each other. There is exactly one cycle, and almost everything is inside it.
2. **The cycle is built by 64 upward edges `core/* → feature/*`.** 23 come from `core/di`, which is
   the DI aggregator and is supposed to see every feature. The other 38 are inverted dependencies —
   `core` code importing feature models, ports and screens. Examples: `core/sync/SeedPlanner.kt`
   imports `NotesRepository`, `ProjectsRepository`, `TaskRepository, TagRepository`;
   `core/search/SearchTextIndex.kt` imports `feature.notes.Note`; `core/wipe` imports eight features.
3. **Hotness is concentrated but the hottest cluster cannot move.** `feature/tasks` (131 files, 367
   commits) and `core/ui` (108 files, 261 commits) are the only clusters that pass the "≥100
   production files" test, and both sit inside the cycle.
4. **21 of the 81 clusters are outside every cycle** and can be lifted as they are. Among the hot
   ones: `test/fakes` (25 files, 279 commits), `core/observability` (10 files, 24 commits), then
   `core/files`, `core/reminders`, `core/ids`, `core/error`, `core/coroutines`, `core/platform`.
5. **Test support is the single hottest thing in the module.** `test/fakes/FakeRepositories.kt` has
   187 commits — more than any production file — and it lives in `commonMain`, so every edit to it
   recompiles all 1,298 production files. `FakeAppDatabase.kt` is third at 113.

## Candidates, with the cut each one needs

A cluster can become a Gradle module only if removing it leaves no path back to it. "Shortest cycle"
is the smallest set of edges that has to be broken first.

| cluster | files | commits | shortest cycle through it | cut needed |
|---|---|---|---|---|
| `test/fakes` | 25 | 279 | — (outside every cycle) | none |
| `core/ui` | 108 | 261 | `core/ui → core/search → feature/notes → core/ui` | `core/search/SearchTextIndex.kt` imports `feature.notes.Note` |
| `core/backup` | 50 | 137 | `core/backup → core/auth → core/log → core/backup` | one of the three edges, all core→core |
| `core/observability` | 10 | 24 | — (outside every cycle) | none |
| `feature/tasks` | 131 | 367 | `feature/tasks → core/attachments → feature/tasks` | 16 mutual edges; not liftable now |
| `feature/agenda` | 50 | 221 | `feature/agenda → core/settings → feature/agenda` | 5 mutual edges |
| `core/sync` | 44 | 155 | `core/sync → core/auth → core/sync` | 6 mutual edges |

The cut that blocks `core/ui` is `core` importing `feature`; the one that blocks `core/backup` is
`core` importing `core`. Nothing here is a size problem — it is a dependency-direction problem.

A module boundary drawn above these is cheap (everything depends on them, they depend on nothing);
a boundary drawn *through* them is not.

## KMP constraints on any candidate

- `core/ui` has **18 `expect`/`actual` declarations** and 13 platform files: it must stay a KMP
  module with the same targets, not a JVM one.
- `commonMain` cannot depend on a `jvm`-only module, so a split of any `commonMain` cluster produces
  another KMP module. The one `expect/actual` seam today is `platformModule()`
  (`docs/PLATFORM-REFERENCE.md`); a new module must not add a second seam without an ADR.
- `:core-database` (Room/KSP) is outside this map by design and must not be pulled into a hot cluster.
- `easement.yml` has `layers` and `no_cycles: true`: today's `shared → {adr-core, core-base}` rule is
  satisfied only because everything is in one component. A new module needs a layer and a
  `may_depend_on` rule, and the rules must not create a cycle — which is another way of stating the
  finding above.
- Koin: per-domain `*DiModule()` returning a list; the aggregator stays thin. `core/di` has 2 incoming
  and 51 outgoing cluster edges — it is a connector, not a candidate.

## What this map cannot see

- Koin resolution and KSP/Room generated code are runtime/compile-time wiring, not imports.
- Reflection and `@Composable` dispatch are plain imports here, but a composable's *call sites* are
  invisible to a package graph — `core/ui` is called from nearly every feature screen.
- 38 upward edges were checked at source level for the ones quoted; the rest come from the same
  longest-prefix resolution and should be re-checked file by file before any of them is cut.
- The graph says what *can* be separated, not what *should*. The compile-price question is Phase 2/3.

## What Phase 1 supports

The cheapest split the data supports is **`test/fakes`**: outside every cycle, 25 files, 279 commits,
and the hottest file in the repository. The first split that looks like a feature boundary is
**`core/ui`**, after cutting `SearchTextIndex.kt`'s dependency on `feature.notes.Note`.

Both are business decisions for Phase 3; Phase 1 only says which ones are possible without refactoring
first, and that every hot *feature* cluster is currently impossible.
