# Phase 1 — hot clusters, and what it would take to move one

Window: commits since 2026-05-05 (1,428 commits touching `shared/src`), tree at `2b4cf8318`.
Generated by `analyse.py --since 2026-05-05`; every number below is copied from `cluster-data.tsv`,
`cut-plan.txt`, `commit-profile.txt`, `hot-files.txt`, `hot-packages.txt`, `co-changes.txt` or
`package-graph.txt` in this directory.

Production = `commonMain` + `jvmMain` + `androidMain`, 1,298 files. Test source sets (669 files) are
counted apart: a hot test file says where the tests are, not where a module boundary belongs.

## What the numbers say

1. **`:shared` is one strongly connected component.** 183 of 243 packages, and 52 of 81 clusters, can
   all reach each other. There is exactly one cycle, and almost everything is inside it.
2. **`core` imports `feature` in 64 places.** 26 come from `core/di`, which is the DI aggregator and is
   supposed to see every feature; 38 are inverted dependencies — `core` code importing feature models,
   ports and screens. Examples: `core/sync/SeedPlanner.kt` imports `NotesRepository`,
   `ProjectsRepository`, `TaskRepository`, `TagRepository`; `core/search/SearchTextIndex.kt` imports
   `feature.notes.Note`; `core/wipe` imports eight features. The shell, the preview screens and the
   test support add 31 more such edges, which is normal for a composition root.
3. **Nothing hot can move without refactoring.** The cost of lifting a cluster is every edge into it
   from a cluster it can itself reach — not the one cycle a shortest-path search finds. `core/ui`: 28
   edges. `feature/tasks`: 26. Every `core/*` together: 217. A greedy feedback arc set for the whole
   cluster graph is 69 edges, so "the 64 upward edges" was never the bill.
4. **Even with every cut made, the win is small: 40 of 1,428 commits (2.8 %)** touch only clusters that
   live outside every cycle. `test/fakes` — the only hot cluster in that set — is the sole cluster of
   10 commits, and appears in 279.
5. **The history understates the clusters that were reorganised.** 297 files were renamed inside the
   tree during the window; 101 landed in `feature/calendarSync`, 37 in `feature/tasks`. A renamed
   file's new path carries only the commits after the rename, so those clusters' counts are lower
   bounds — `feature/calendarSync`'s 18 commits is an artifact, not a cold feature.

## What lifting one cluster actually costs

A cluster `X` becomes a module only if nothing it can reach imports it back, so the exact cost is
**every edge `Y → X` where `Y` is reachable from `X`**. Cutting one shortest cycle does not free `X`,
and `cut-plan.txt` holds the check.

| lift | clusters | edges to cut |
|---|---|---|
| `test/fakes` | 1 | **0** |
| `core/observability` | 1 | **0** |
| `(root)` — the shell | 1 | **0** |
| `core/backup` | 1 | 4 |
| `feature/tasks` | 1 | 26 |
| `core/ui` | 1 | 28 |
| every `core/*` | 39 | 217 |
| the whole graph as a DAG | — | 69 (greedy FAS, an upper bound) |

Two claims from an earlier draft are wrong and are corrected here:

- **"`core/ui` needs one cut (`core/search → feature/notes`)."** Cutting exactly that edge leaves
  `core/ui` in a cycle and the largest SCC at 52. It needs 28.
- **"The cycle is held by these 64 edges, so that is the work."** Moving the DI aggregator out of the
  graph — removing the 2 edges *into* `core/di`, which is where it belongs — takes the largest SCC from
  52 to 50. The inversions are the symptom; the work is a layer refactor measured in tens of edges.

## What share of the history a split could shorten

| commits | what |
|---|---|
| 40 (2.8 %) | touch only clusters outside every cycle — the upper bound for a split with no refactoring |
| 10 (0.7 %) | touch only `test/fakes` |
| 279 (19.5 %) | touch `test/fakes` at all — those still recompile `:shared` |

So the one split that is free today, `test/fakes`, would shorten about 10 commits out of 1,428. Its
co-change partners (`core/di` in 139 commits, `feature/tasks` in 105) keep the rest of the module
recompiling — the same statement from the other side.

A boundary above these is cheap — everything depends on them, they depend on nothing. A boundary drawn
*through* them is not, and they are why every cut list above is long.

## KMP constraints on any candidate

- `core/ui` has 18 `expect`/`actual` declarations and 13 platform files: it must stay a KMP module with
  the same targets, not a JVM one.
- `commonMain` cannot depend on a `jvm`-only module, so lifting any `commonMain` cluster produces
  another KMP module. The one `expect/actual` seam today is `platformModule()`
  (`docs/PLATFORM-REFERENCE.md`); a new module must not add a second seam without an ADR.
- A test-support module is not free either: `:shared`'s `commonTest` would depend on a module that
  depends on `:shared`. Gradle tolerates test-configuration cycles in `testFixtures`, but that plugin
  is JVM-only and this is a KMP module — **unverified, and it decides whether `test/fakes` can move at
  all**. It is a two-module probe, not a guess.
- `:core-database` (Room/KSP) stays out of any hot cluster; KSP runs on every edit in its module.
- `easement.yml` (`layers`, `no_cycles: true`) will reject a module boundary that creates a cycle —
  another way of stating the finding above.
- Koin: per-domain `*DiModule()` returning a list, aggregator thin. `core/di` has 2 incoming and 51
  outgoing cluster edges — a connector, not a candidate.

## What this map cannot see

- Koin resolution and KSP/Room generated code are runtime/compile-time wiring, not imports.
- A composable's call sites are imports, but their *frequency* is not — `core/ui` is called from nearly
  every screen, so its 28 inbound cuts understate the real coupling.
- The 38 upward edges were spot-checked at source level where quoted; the rest come from the same
  longest-prefix resolution and must be re-checked file by file before being cut.
- The graph says what *can* be separated, not what *should*. The compile-price question is Phase 2/3.

## Conclusion for the plan

The data says the plan's ordering is wrong, not its premise. A split cannot shorten UI/ViewModel edits
until the layer inversions are gone, and the inversions are tens of edges, not four. The cheap next
step is **layer repair, then split**:

1. Cut the 38 `core → feature` inversions and move `core/di` above the graph. That is a refactor with
   its own tests, and it is the precondition for any module boundary.
2. Only then does Phase 2 (cost model) inform a decision — modelling module sizes before the graph can
   be cut would price a split that cannot exist yet.

Phase 2 is therefore deferred. `test/fakes` is filed as a side question — worth 10 commits, blocked on
the KMP test-support dependency above — not as the pilot.
