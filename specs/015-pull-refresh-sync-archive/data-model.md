# Data Model: Pull-to-refresh — синхронизация и перенос завершённого в архив

**Feature**: `specs/015-pull-refresh-sync-archive`
**Date**: 2026-10-25
**Phase**: 1 (design)

Схема хранения **не меняется**. Фича не добавляет ни таблиц, ни столбцов, ни
миграций: перенос в архив работает с уже существующими полями задачи
(`completed_at`, `archived_at`), а синхронизация — с уже существующей очередью
отправки. Поэтому здесь нет раздела «миграции», и экспорт схемы Room не
перевыпускается.

Ниже — только новые типы и те, что меняют форму.

---

## Типы

### `RefreshOutcome` — результат одного обновления

| Поле | Тип | Смысл |
|---|---|---|
| `archived` | `Result<Int>` | Шаг архивирования: сколько задач перенесено, либо почему не вышло |
| `sync` | `SyncOutcome` | Итог цикла синхронизации в его собственном словаре |

**Правила**

- `archived` — `Result<Int>`: успех означает число **перенесённых этим запуском**
  задач, а не общее число завершённых задач в профиле. Ноль — успешный результат
  («переносить было нечего»), а не ошибка.
- `sync` — существующий `SyncOutcome` (`core/sync/SyncEngine.kt:97-129`) без
  изменений: `Completed(push, pull)` / `CouldNotStart(error)` / `NothingToDo`.
- Два поля независимы: сбой шага архивирования **не** отменяет синхронизацию, и
  сбой синхронизации **не** отменяет архивирование. Именно это делает FR-007 и
  FR-017 независимыми требованиями, а не одним.
- `SyncOutcome.NothingToDo` означает, что активной области синхронизации нет —
  то есть пользователь не вошёл в аккаунт. Это отдельный случай в сообщении, а
  не ошибка.

**Происхождение:** `core/refresh/RefreshOutcome.kt` — новый файл.

### `RefreshUiState` — состояние общего ViewModel

| Вариант | Поля | Когда |
|---|---|---|
| `Idle` | — | обновление не выполнялось |
| `Refreshing` | — | обновление идёт |

Индикатор жеста показывается в состоянии `Refreshing`. Состояние не содержит
результата: результат — одноразовое событие, а не часть состояния (D-05).

**Происхождение:** `core/refresh/RefreshUiState.kt` — новый файл.

### `RefreshUiEvent` — одноразовые события

| Событие | Поля | Когда |
|---|---|---|
| `Finished` | `outcome: RefreshOutcome` | обновление завершилось, успешно или нет |

Один вариант на все исходы: различает их `RefreshOutcome`, а не тип события.
Разбор исхода в сообщение пользователя живёт в одном месте — в отображении
результата, — а не в семнадцати экранах.

**Происхождение:** `core/refresh/RefreshUiEvent.kt` — новый файл.

### `CompletedTaskArchiver` — порт ядра

```kotlin
interface CompletedTaskArchiver {
    suspend fun archiveCompletedTasks(): Result<Int>
}
```

Один метод. Порт архива `ArchiveRepository`
(`feature/archive/domain/port/ArchiveRepository.kt:7`) наследует его, поэтому
реализация не меняется ни на строчку.

**Правила**

- Метод возвращает число перенесённых задач.
- Перенос затрагивает только активный профиль — это уже обеспечено реализацией
  (`TaskDaoArchiveRepositoryImpl.kt:39-41`).
- Задачи, уже лежащие в архиве, повторно не переносятся — это обеспечено тем же
  запросом (`archived_at IS NULL`).

**Происхождение:** `core/refresh/CompletedTaskArchiver.kt` — новый файл;
`feature/archive/domain/port/ArchiveRepository.kt` — одна строка меняется.

### `RefreshCoordinator` — владелец запуска

Не тип данных, а владелец состояния. Держит:

| Поле | Тип | Смысл |
|---|---|---|
| `scope` | `AutoCloseableCoroutineScope` | scope синглтона; запуск живёт в нём |
| `triggers` | `Channel<Unit>` | conflating-канал запросов |
| `completedRuns` | `MutableStateFlow<Long>` | счётчик завершённых запусков |
| `lastOutcome` | `MutableStateFlow<RefreshOutcome?>` | результат последнего запуска |

Поле `lastOutcome` существует, чтобы экран, вернувшийся на место после ухода,
мог показать результат (крайний случай спецификации). Оно **не** является
источником отчёта для всех экранов: отчёт выдаёт вызвавший (D-05).

**Происхождение:** `core/refresh/RefreshCoordinator.kt` — новый файл.

## Отношения

```text
RefreshCoordinator (синглтон, scope приложения)
├── CompletedTaskArchiver  ──▶ ArchiveRepository ──▶ TaskDaoArchiveRepositoryImpl
│                              (наследует порт ядра)     (привязка в core/di/TasksDiModule.kt)
└── SyncRepository (публичный фасад) ──▶ SyncCoordinator ──▶ SyncEngine

RefreshViewModel (на каждый экран)
└── RefreshCoordinator  (тот же синглтон)

RefreshableContent (общий composable)
└── RefreshViewModel (через koinViewModel())
```

Путь `RefreshCoordinator → SyncRepository → SyncCoordinator` не образует цикла:
`SyncCoordinator` не знает ни об обновлении, ни о чём, что знает `RefreshCoordinator`.

## Инварианты

| Инвариант | Где обеспечивается |
|---|---|
| Один запуск обновления за раз | conflating-канал координатора |
| Архивирование до синхронизации | порядок шагов в координаторе (D-02) |
| Архив уходит на сервер в том же обновлении | архивирование кладёт задачи в очередь отправки до фазы отправки |
| Перенос затрагивает только активный профиль | `TaskDaoArchiveRepositoryImpl` |
| Задачи в архиве не переносятся повторно | условие `archived_at IS NULL` |
| Результат одноразовый | событие в канале ViewModel с ёмкостью `BUFFERED` |
| Ядро не зависит от портов фич | собственный порт `CompletedTaskArchiver` (D-11) |

---

## Что не меняется

| Объект | Почему не меняется |
|---|---|
| Схема Room и экспорт схем | новых полей нет |
| `SyncOutcome` | словарь исходов уже различает нужные случаи |
| `ArchiveRepository` | реализация уже делает нужное, включая постановку в очередь отправки |
| Восемнадцать существующих ViewModel экранов | обновление — чужая подсистема (D-09) |
| Плановая синхронизация и её интервал | обновление добавляется к ней, а не заменяет |
