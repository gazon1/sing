# Quickstart: проверка фичи «обновление жестом»

**Feature**: `specs/015-pull-refresh-sync-archive`
**Дата**: 2026-10-25

Руководство по проверке: как убедиться, что обновление жестом работает, от
модульных сценариев до ручной проверки на двух устройствах. Реализация не
приводится — она в `tasks.md` и в коде.

---

## Предусловия

- JDK 21, `./gw` на PATH репозитория (свой `GRADLE_USER_HOME` — общий `~/.gradle`
  блокирует кэш модулей).
- Хост не занят: `./sg host-load` (порог 2.0 на ядро). Если занят — сначала
  целевой набор тестов, полный прогон позже.
- Для ручных сценариев: два устройства с одним аккаунтом, либо приложение на
  настольном компьютере и на телефоне.

---

## Порядок проверки

```bash
# 1. Компиляция сразу после связной правки — иначе падение компиляции
#    прячется за «упало в тестах».
./gw :shared:compileKotlinJvm

# 2. Целевые тесты фичи.
./gw :shared:jvmTest --tests "com.singularity.todo.core.refresh.*"
./gw :desktopApp:test --tests "com.singularity.todo.core.refresh.*"

# 3. Detekt по изменённым файлам (он же — в pre-commit).
just lint-changed

# 4. Полный набор гейтов перед коммитом.
just gate
```

Долгие запуски — одной фоновой задачей с логом в уникальный файл, ожидание —
одним вызовом:

```bash
./gw :shared:jvmTest > build/diagnostics/jvmTest-refresh.log 2>&1 &
./wait-for build/diagnostics/jvmTest-refresh.log "BUILD"
```

## Сценарии проверки

### V-01 — Архивирование происходит до синхронизации

**Где:** модульный тест координатора обновления.

**Как:** подменяются оба шага записывающими заглушками; выполняется одно
обновление; порядок вызовов фиксируется.

**Ожидание:** вызовы идут в порядке «архивирование → синхронизация». Это то, из-за
чего состояние архива уходит на сервер в рамках того же жеста.

### V-02 — Параллельные запросы не создают второго обновления

**Где:** модульный тест координатора обновления.

**Как:** один запрос уже выполняется; приходит второй.

**Ожидание:** шаг архивирования выполнен один раз, цикл синхронизации — один раз,
оба запроса получили один и тот же результат.

### V-03 — Результат превращается в ожидаемое сообщение

**Где:** модульный тест разбора результата.

**Как:** по одному варианту на строку таблицы контракта
`contracts/refresh-outcome.md`.

**Ожидание:** для каждого варианта — своё сообщение; при нуле перенесённых
задач это «переносить было нечего», а не ошибка.

### V-04 — Жест действительно запускает обновление

**Где:** тест общего контейнера на настольном приложении
(`desktopApp/src/jvmTest`).

**Как:** содержимое помещается в контейнер; выполняется жест.

**Ожидание:** обновление запущено один раз; индикатор появляется и исчезает;
содержимое при этом прокручивается.

**Почему этот сценарий обязателен.** Фича, которая «готова, но ничего не делает», —
самый частый дефект: код компилируется, покрыт тестами и не вызывается никем.
Проверка, что жест доходит до координатора, закрывает именно его.

### V-05 — Отчёт появляется на экране

**Где:** тест общего контейнера на настольном приложении.

**Как:** обновление завершается результатом с числом перенесённых задач.

**Ожидание:** в области уведомлений появляется сообщение с этим числом.

### V-06 — Отчёт переживает уход с экрана

**Где:** модульный тест общего ViewModel обновления.

**Как:** обновление запускается; экран «покидается» (ViewModel остаётся жив);
результат приходит после.

**Ожидание:** событие с результатом буферизовано и будет показано при возвращении.

### V-07 — Без сети архивирование всё равно происходит

**Где:** модульный тест координатора обновления.

**Как:** синхронизация возвращает ошибку.

**Ожидание:** задачи перенесены в архив, в результате — и успех архивирования, и
ошибка синхронизации; сообщение говорит и про архив, и про сбой.

### V-08 — Состояние архива доходит до второго устройства

**Где:** ручная проверка, два устройства с одним аккаунтом.

**Как:**

1. На устройстве А отметить задачу выполненной.
2. На устройстве А выполнить обновление жестом.
3. На устройстве Б выполнить обновление жестом.

**Ожидание:** задача на устройстве Б ушла в архив, а не вернулась в рабочий
список. Если задача вернулась — состояние архива не ушло на сервер, и FR-015
не выполнен.

## Результаты проверки

Запуск: 2026-10-25, ветка `015-pull-refresh-sync-archive`.

| Сценарий | Где проверяется | Результат |
|---|---|---|
| V-01 | `RefreshCoordinatorTest` → `the archive step runs before the synchronisation step` | пройден |
| V-02 | `RefreshCoordinatorTest` → `a second request during a running refresh joins it` | пройден |
| V-03 | `RefreshOutcomeMessageTest` — по одному случаю на строку таблицы | пройден (9 случаев) |
| V-04 | `RefreshableContentTest` → `the gesture reaches the coordinator and the report appears in the notification host` | пройден |
| V-05 | тот же тест — сообщение появляется в области уведомлений | пройден |
| V-06 | `RefreshViewModelTest` → `the outcome is buffered while nobody listens and arrives when the screen comes back` | пройден |
| V-07 | `RefreshCoordinatorTest` → `a failed synchronisation leaves the archive result intact` | пройден |
| V-08 | ручная проверка, два устройства | **не выполнено** |

**V-08 не выполнено — почему.** На машине нет ни эмулятора, ни подключённого
устройства, поэтому проверить путь «архив уходит на сервер в рамках того же
жеста» вручную было нечем. Сценарий остаётся непроверенным, и это надо сказать
открыто, а не считать выполненным по косвенным признакам.

Что говорит в его пользу: архивный шаг пишет перенесённые строки в очередь
отправки, а цикл синхронизации читает эту очередь после него — это проверяет
`TaskDaoArchiveRepositoryImplTest` → `bulk archive enqueues every newly archived
task`. Чего тесты не покрывают — самого сетевого обмена с сервером, поэтому
проверка на двух устройствах остаётся обязательной перед выпуском.

**Что ещё не проверено.** Ручная проверка на устройстве (таблица наблюдений
ниже) тоже не выполнялась: без устройства её не с чем сверять.

## Ручная проверка на устройстве

```bash
# Запуск на эмуляторе — скилл singularity-todo-emulator-launch.
adb shell am start -n <package>/.MainActivity

# Экран вкладок: потянуть список вниз и отпустить.
```

Что смотреть:

| Наблюдение | Что означает |
|---|---|
| Индикатор тянется за пальцем и спиннер виден | жест подхвачен (D-10) |
| Список прокручивается, пока обновление идёт | экран не заблокирован (FR-004) |
| Второй жест во время обновления не запускает второе | FR-003 |
| Сообщение после обновления содержит число | FR-016 |
| Сообщение после обновления содержит «синхронизация не удалась» при выключенной сети | FR-017 |
| Завершённая задача исчезла из рабочего списка | FR-011 |
| Завершённая задача появилась в архиве | FR-011 |

## Экраны без прокрутки

Контейнер прокрутку не даёт: прокручиваемый контейнер измеряет своё содержимое
без ограничения по высоте, и содержимое, заполняющее экран, схлопнулось бы. Поэтому
прокрутка остаётся у экрана, а контейнер поднимается над ней (см. `research.md`,
D-07).

Детальная задача уже имела свою прокрутку — в каркасе редактора
(`feature/tasks/presentation/components/detail/TaskEditorContent.kt:173`); её
структура не менялась. Прокрутку получил только Помодоро
(`feature/pomodoro/PomodoroScreen.kt:74`) — на своём корне, в порядке
`fillMaxSize().padding().verticalScroll()`, который использует остальной код.
Проверяется отдельно: на Помодоро жест должен срабатывать, и содержимое не должно
«прыгать» при появлении прокрутки.

## Признак «фича готова, но ничего не делает»

Проверка, которая закрывает этот класс дефекта: `scripts/find-unwired-surfaces.py`
находит реализованные, но не вызываемые поверхности. Запустить после того, как
контейнер подключён к экранам, и убедиться, что он вызывается из каждого
экрана охвата.
