## D-01 — Прикреплённая заметка создаётся на первом сохранении

**Decision**: «+» в логбуке открывает редактор без записи в БД; заметка создаётся первым
сохранением, уже с `task_id`.

**Rationale**: пустая заметка не должна появляться (решение пользователя №2); побочно исчезает
расхождение между «создали строку» и «сохранили содержимое», из которого вырос баг. Это
восстанавливает задокументированное намерение (ADR `2026-09-22`, KDoc `Editing.isNew`), а не
вводит новое.

**Alternatives considered**:
- (а) создавать при открытии и чинить только запись — остаются мусорные «(untitled)»-строки;
- (б) создавать при открытии и удалять при выходе без текста — лишний путь удаления с гонкой
  (черновик мог быть изменён, а заголовок — пустым); пользователь отверг этот вариант в опросе.

## D-02 — id заметки принадлежит вызывающему

**Decision**: `createForTask(id: NoteId, taskId: TaskId, …)`; репозиторий пишет переданный id.

**Rationale**: у черновика уже есть id (`idGen.next()`), он же уходит в бэк-стек и в
последующие точечные `UPDATE`; при расхождении id `updateContent` не найдёт строку
(`require(rows > 0)` → «Note … not found»). Это же требование домашней примитивы `create`
(«ID generated by caller or IdGenerator»).

**Alternatives considered**:
- (а) редактор подхватывает id, возвращённый репозиторием, — осиротевшая запись
  черновик-хранилища под старым id;
- (б) новый порт-метод `createForTaskWithId` — дублирование одного метода.

## D-03 — Инвариант живёт в выборе примитивы, а не в списке полей

**Decision**: привязка пишется один раз, при создании; все последующие сохранения — точечный
UPDATE, перечисляющий только колонки содержимого. Слияние структурных полей в Kotlin **не**
вводится.

**Rationale**: домашняя модель делит запись на `create` (полная строка) и `edit`
(read-modify-write); баг — это `create`, применённый к существующей строке. Список полей в
Kotlin — ловушка: новая колонка `NoteEntity` забудется в списке, и баг вернётся.

**Alternatives considered**:
- (а) read-modify-write слияние в `createWithContent` — отвергнуто (см. §7 плана);
- (б) DAO-уровень `ON CONFLICT DO UPDATE SET` с явным списком колонок — лишний сырой SQL и
  вопрос совместимости SQLite на API 26+ (UPSERT требует SQLite 3.24).

## D-04 — Один writer на оба пути сохранения

**Decision**: `AutosaveContext.writeNote(draft)` обслуживает и автосейв, и `persist`.

**Rationale**: расхождение двух копий ветки create/update и есть тот класс дефекта, который
чиним. Побочные выигрыши: автосейв перестаёт «успевать» до записи (`launch` + возврат
немедленно → базовый класс считал сохранение успешным до его завершения), ошибка автосейва
перестаёт теряться в логе, а `outgoing_links` пишется при каждом сохранении, а не только при
явном Save.

**Alternatives considered**: править обе копии — регрессия вернётся при следующей правке.

## D-05 — Логбук = только структурно прикреплённые заметки

**Decision**: в логбуке только заметки с `notes.task_id`; union по `outgoing_links` не делаем;
KDoc `watchForTask` переписывается с «via wikilinks» на «attached to a task».

**Rationale**: решение пользователя №1; `task_id` — источник истины (ADR `2026-10-01`),
заметки со ссылками уже показываются в карточке «Связанное».

**Alternatives considered**: union `task_id ∪ outgoing_links` — размывает семантику, требует
правки DAO-запроса и его тестов, и меняет поведение seeded-фикстур (`seed.yaml … linkTo=`
пишет только `outgoing_links`).

## D-06 — Точечный UPDATE вместо полной перезаписи строки

**Decision**: правка существующей заметки идёт через `updateContent` (ownership-scoped UPDATE).

**Rationale**: KDoc-обещание `buildPersistedNote` (собрать полную заметку и записать `upsert`)
описывает несуществующий механизм; `cachedNote` — устаревший снимок, и полная перезапись
вернула бы в БД поля, уже обновлённые rewrite-watcher'ом, и затерела бы sync-метаданные
(`hlc`, `server_version`).

**Alternatives considered**: `repo.update(mergedNote)` — тот же риск; «обновлять `cachedNote`
перед каждой записью» — та же гонка, только сложнее.

## D-07 — Убрать мёртвое состояние и починить документацию

**Decision**: удалить `cachedNote` (пишется в трёх местах, не читается ни разу) и параметр
`preExistingId`; переписать KDoc редактора (`:56-59` — обещает несуществующий
`buildPersistedNote`; `:200-206` — «saved to the DB immediately»; `:225-230`) и KDoc
`Note.taskId` (`Ids.kt` — обещает запись `task://`-токена, чего уже нет после ADR `2026-10-02`).

**Rationale**: расхождение «документация ↔ код» пропустило баг в релиз. KDoc редактора
прямо утверждал, что `taskId` сохраняется при автосейве, — и это было неправдой.

**Alternatives considered**: оставить поле «на будущее» — оно уже один раз солгало.

## D-08 — Незатронутый черновик не записывается

**Decision**: автосейв пропускает черновик, который `isNew && !isDirty`; `onAutosaved` в этом
случае не снимает флаги.

**Rationale**: автосейв — debounce по *изменениям* черновика, а `open(draft)` — тоже
изменение, поэтому открытие редактора создавало бы пустую заметку через 500 мс. Без явного
правила решение пользователя №2 («пока не сохранил — заметки нет») не выполняется. Побочный
эффект правила убирает мусорную строку того же класса, что и исходный баг.

**Alternatives considered**:
- (а) править базовый `DraftMviViewModel` (фильтровать автосейв по `isDirty` для всех
  редакторов) — расширяет blast radius на редактор задач;
- (б) удалять заметку при выходе — пользователь отверг этот вариант в опросе.

## D-09 — Четыре testTag'а, категория «Tasks» в золотом каталоге

**Decision**: `LOGBOOK_SECTION`, `LOGBOOK_EMPTY`, `LOGBOOK_ADD_NOTE_BUTTON`, динамический
`logbookNoteByTitle(title)`; в `TagsMd.kt` — правило `"LOGBOOK_" → "Tasks"` и строка
`dynamicMeta`; `Maestro/TAGS.md` перегенерируется.

**Rationale**: без тегов флоу не может дождаться раздела и адресовать строку; категория
«Tasks» вместо новой секции «Logbook» — чтобы не трогать `staticSubsections`/`dynamicSubsections`.

**Alternatives considered**: адресовать по тексту — хрупко (локализация, дубли строк) и
противоречит конвенции «контролы — по id».

## D-10 — E2E-флоу на реальном устройстве, сценарий `TASK-LOG-01`

**Decision**: `Maestro/flows/tasks/logbook/TASK-LOG-01.yaml`, теги `regression`, `tasks`,
`scenario:TASK-LOG-01`; `targets: [android]`; фикстура — штатный `helpers/seed-task.yaml`
(«Buy milk»), заметка создаётся **из логбука**.

**Rationale**: путь «создать из логбука» — единственный сломанный; засеять готовую заметку
значило бы протестировать не то (seed-linked заметка пишет только `outgoing_links`, см. D-05).

**Alternatives considered**: desktop-tier Compose-тест того же пути — дешевле по времени, но
не проверяет навигацию между графами, ради которой флоу и нужен.

## D-11 — ADR обязателен: меняется контракт слоя данных

**Decision**: `docs/decisions/2026-10-25-task-logbook-note-attachment.md`, `status: open`;
после — `./scripts/refresh-decisions-digest.sh`.

**Rationale**: конституция требует ADR при изменении паттерна слоя данных; меняются сигнатура
порта и семантика записи, а решение «почему не полная перезапись строки» иначе нигде не
записано.

**Alternatives considered**: обойтись как «bug fix» — не подходит: поведение меняется.

## D-12 — OpenSpec-изменение не заводим

**Decision**: работа живёт в `specs/015-fix-task-logbook/` + ADR; каталога
`openspec/changes/<slug>/` не создаём.

**Rationale**: конституция относит bug fixes к случаям без OpenSpec; гейты
(`check-issue-registry.py`, `check-review-verdicts.py`) проверяют только существующие каталоги
`openspec/changes/` и новых не требуют.

**Alternatives considered**: завести OpenSpec-изменение «на всякий случай» — лишняя церемония
и ревью-вердикт, который никто не просил.
